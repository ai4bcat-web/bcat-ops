# Rate-con batch — logo, sender cc, recipient picker, MCP-complete gate (ships in the S2 deploy)

Four additive rate-confirmation changes, planned against the code on `dev` as it stands (S1 deployed). **Out of scope, explicitly:** covering several carriers on one load at once (multi-carrier) — nothing here touches `BOOK_CARRIER`, the one-ACTIVE-assignment rule, or the `LoadCarrier` shape.

Batch rule (`TMS_BUILD_BRIEF.md`): this work and S2 go out in **one** Amplify deploy; no doc-only deploy. This plan is a doc and rides that deploy with the code.

## 1. Decisions

**D1 — (a) Logo is resolved in the browser, inside `buildRateConPdf`, with an injectable loader.** `buildRateConPdf(input, options?: { loadLogo?: (logoKey: string) => Promise<string | null> })`; default loader = new `fetchDivisionLogoDataUrl` in `src/lib/divisionLogo.ts`. The second arg is optional so the three existing callers (`RateConPanel`, `dispatch/rateCon.ts`, `GeneratedDocumentDialog`) are **not edited** and all get the logo. Rejected: pre-resolving in each caller (3 edits, easy to forget one, and each would need async work before building the input).

**D2 — Logo loading rules (`fetchDivisionLogoDataUrl(logoKey) → string | null`, never throws).** `getUrl({ path: logoKey, options: { expiresIn: 300 } })` → `fetch(url)` with a 5 s `AbortController` timeout → `!res.ok` ⇒ `null` → read the bytes and **sniff the magic number** (PNG `89 50 4E 47`, JPEG `FF D8 FF`; anything else — SVG, WebP, HTML error page — ⇒ `null`, the stored content-type is not trusted) → size cap 2 MB ⇒ else `null` → return `data:image/png|jpeg;base64,…`. `buildRateConPdf` then calls `doc.getImageProperties(dataUrl)` inside its own `try`; any throw ⇒ no logo. **Absent `logoKey`, loader `null`, loader throw, undecodable image ⇒ identical fallback: today's text header.** A missing/blocked logo can never fail a send.

**D3 — Header layout with a logo.** The band is black, and brand logos usually have dark elements, so (same house pattern as `payPdf.ts`) the logo sits on a **white rounded plate** inside the band: fit to a 150×38 pt box preserving aspect ratio, plate `roundedRect(M-8, 10, w+16, 50, 5, 5, 'F')`, `doc.addImage(dataUrl, format, M, 16, w, h, 'division-logo')` — the fixed alias makes jsPDF embed the image **once** for a multi-leg / continuation document (`drawHeader` runs once per page). The **legal name stays printed** (legal-identification line: 11 pt bold white `broker.name`, then the existing grey `MC … · DOT …` line, left edge `M + plateW + 10`, clipped with `splitTextToSize` to the room left of the right-hand "RATE CONFIRMATION" block, i.e. ≤ `W - M - 150 - x`). Without a logo the header is byte-for-byte today's (16 pt name at `M, 34`). `stampSignature` appends a page with pdf-lib and is untouched.

**D4 — (b) The sender is cc'd by the Lambda, not by the UI.** In `sendRateCon` the final list is built by a new pure helper `composeRateConCc({ to, extraCc, tracking, sender })`: order `tracking mailbox, …typed cc (in order), sender`; **case-insensitive dedupe, first spelling wins**; anything already in `to` is dropped from `cc` (To wins — no one gets two copies); `to` itself is deduped the same way before it is stored/sent. `sender` = `caller.email`, added **only if it passes `isEmailAddress`** (same regex as `assertEmail`); if it does not, the send proceeds without it, `console.warn`s, and the audit row records `senderCc: null`. That final `cc` is the one used for the MIME header, the SES `CcAddresses`, the `ShipmentMessage.cc` column and the audit row (no divergence). Server-side so every path (panel, suggestion button, offer queue, scripts) copies the sender, and the UI cannot forget or spoof it.

**D5 — One email validator for UI and Lambda.** New `src/lib/emailAddress.ts` (pure, relative-import safe) holds the exact rule `assertEmail` uses today (`≤200 chars`, `^[^\s@,;<>"]+@[^\s@,;<>"]+\.[^\s@,;<>"]+$` — blocks CR/LF/comma header injection). `handler.ts`'s `assertEmail` is rewritten on top of it; the picker validates with it. One rule, so a UI-accepted address is never server-rejected.

**D6 — (c) Picker lives in `RateConPanel` only.** "Known emails" = every **active** `CarrierContact` with a valid email, then `LoadCarrier.dispatcherEmail` ("Dispatcher on this booking"), `Carrier.dispatcherEmail`, `Carrier.email`; deduped case-insensitively, malformed stored addresses are not offered. **Pre-selected = exactly today's default** (contacts flagged `rateConRecipient` or typed `DISPATCH`; if none, the carrier's dispatcher/main email) — behaviour for someone who just clicks Send is unchanged. Below the checkbox list: one "Add another address" input (+ Add button / Enter) for typed addresses, validated with `isEmailAddress`; added addresses appear as removable chips and are always selected. A half-typed address in the box is **committed on Send; if invalid, Send is blocked** (never silently dropped). Zero recipients ⇒ Send disabled. The CC box stays a free text field but is validated per token with the same rule before Send, and a read-only line says "You (<email>) are copied automatically" (from `useAuthUser()`). The two one-click paths (suggestion button, offer queue) keep the default recipients — they have no UI to host a picker, and the brief asks for the *send UI*.

**D7 — (d) What "completed MyCarrierPackets packet" means — one pure predicate shared by Lambda and UI.** New `src/lib/mcpPacket.ts`: a carrier's packet is **completed iff its `mcpStatus`, normalised (trim, upper-case, runs of space/hyphen → `_`), is one of `PENDING_REVIEW, ACCEPTABLE, MODERATE, UNACCEPTABLE, UNACCEPTABLE_REVIEW`** — i.e. the carrier has finished the packet and MCP has received it (review pending or risk-assessed). **Not completed:** blank/`null`, `NOT_INVITED`, `INVITED`, `IN_PROGRESS`, and **any other free text** (hand-typed `'Ready'`, `'APPROVED'`, …) — an unrecognised word is not evidence a packet exists. Reasons: why this field and not `mcpPacketCompletedAt` — that attribute is not in the GraphQL model (UI cannot read it, AppSync would drop it on write), and its presence depends on an assumed MCP response field; `mcpStatus` is in the schema, selection set, board column and carrier profile badge. Adding `mcpPacketCompletedAt`/`mcpReviewStatus` to the `Carrier` model is the *rejected* alternative: it is additive but forces a data (schema) deploy for no behavioural gain; if Main wants it later it is a one-line addition to the predicate (`|| Boolean(carrier.mcpPacketCompletedAt)`).

**D8 — Completion ≠ approval (literal reading of the ask).** `UNACCEPTABLE` / `UNACCEPTABLE_REVIEW` carriers *have* a completed packet and therefore pass *this* gate; the existing approval layer (`coverage.ts` `carrierFlags`: "MyCarrierPackets unacceptable", MODERATE over the risk ceiling; `evaluateCarrierBooking`) is unchanged and still decides whether a carrier is suitable. **Open decision for Main:** if "may be sent a rate con" should also exclude UNACCEPTABLE*, delete those two names from `MCP_PACKET_COMPLETED_STATUSES` and rename the prefix — one constant, tests pin the set.

**D9 — Refusal contract.** Server throws `rateConMcpRefusal(carrierName, standing)` = `Rate confirmation needs a completed MyCarrierPackets packet: <Carrier name> <reason> Send a setup packet from the carrier profile and re-send once MyCarrierPackets reports it complete.` where `<reason>` is: `has no MyCarrierPackets status on file, so no completed packet.` / `has not been sent a MyCarrierPackets packet.` (NOT_INVITED) / `was invited but has not started the MyCarrierPackets packet.` (INVITED) / `has not finished the MyCarrierPackets packet.` (IN_PROGRESS) / `is at MyCarrierPackets status "<raw>", which is not a completed packet.` (other). The stable "code" is the exported `RATE_CON_MCP_ERROR_PREFIX = 'Rate confirmation needs a completed MyCarrierPackets packet'`. The UI shows `standing.reason` (same wording) next to a link to the carrier profile. The gate runs **before any side effect** (before the S3 `PutObject`, token mint, transaction, SES).

**D10 — Gate scope.** Enforced at *send/re-send* only. `VOID_RATE_CON`, copy-link, and a carrier who already holds a live link signing it are unaffected (the gate decides who may be *sent* a rate con, not who may answer one already sent). Own-fleet assignments (`OWN_ASSET`, no `carrierId`) never reach the gate — they already fail `That assignment is not a directory carrier` and are untouched.

**D11 — Demo carriers: no bypass, seed data conforms.** No `BCAT_DEV_STACK` shortcut: dev must exercise the real gate. `seedCarriers` gives **`carr-demo-vetted` `mcpStatus: 'ACCEPTABLE'`** (so the P8 flow and every demo path keeps working); **`carr-demo-lapsed` and `carr-demo-nobuy` get none**, so they are the live "refused" examples. `SEED_VERSION` `p8.1` → `p8.2`. Because the seed is idempotent (a second run is a no-op once any `DemoRecord` exists), an **already-seeded dev stack keeps the old vetted row** until `RESET_DEMO` + `SEED_DEMO` is run (or its `mcpStatus` is set from the Carrier form). `devVerifyP.mjs` gets a fail-fast preflight telling the operator exactly that instead of a confusing refusal at P8.

**D12 — One-click UI paths.** (i) `SuggestionRow` ("Send rate con"): disabled with the reason as hint when `!mcpPacketStanding(carrier).completed`; `handleSendRateCon` re-checks after `getCarrierBundle` and toasts the refusal before building a PDF. (ii) `OfferRow`: for `vetting.bookable && !completed` the primary "Assign carrier + send rate con" is **disabled with the reason**, and "Send setup packet" (existing handler) is shown beside it when `offer.carrierEmail` exists — the setup packet is what makes the carrier eligible. (iii) `bookCarrierAndSendRateCon` fetches `getCarrierBundle` **first** and throws the refusal **before `actions.bookCarrier`**, so a stale vetting snapshot can never leave a carrier booked but refused. (Booking a non-MCP carrier from elsewhere is unchanged; only book-**and-send** is blocked here.)

**D13 — `RateConPanel` gate uses what is loaded.** When `carrier` (from `CarrierSection`'s `getCarrierBundle`) is present: Send/Re-send disabled when `!completed`, notice shown, Preview stays enabled. When `carrier` is `null` (bundle still loading or its read failed — `CarrierSection` keeps stale state on failure) the client does **not** pre-block; the server is the authority and its message lands in the panel's error line. This avoids a permanently dead button on a transient read failure.

## 2. Schema

**None.** `Division.logoKey` exists; `Carrier.mcpStatus` exists; nothing is added, renamed or retyped. No new env vars, no new IAM: `shipmentActionsFn` already has `CARRIER_TABLE_NAME` + read on the directory Carrier table (`BOOK_CARRIER` reads it via `getById(CARRIER_TABLE_NAME, …)`, handler L4360); the browser already has `brand/*` read. Consequence: **this batch by itself needs only a Lambda code deploy and a front-end build, not a data deploy.** (If S2 changes the schema, the single combined deploy is a data deploy anyway — that is S2's cost, not this plan's.)

## 7. Risks

- **R1 — Existing carriers become un-sendable.** Any carrier whose `mcpStatus` is blank or not one of the five completed names (including hand-typed words and carriers MCP has never synced) is refused at send **and at Re-send** — including a rate con already out for such a carrier (Void and Copy link still work). Mitigation: the §6.2 data check; if prod has a legitimate hand-typed vocabulary, widen `MCP_PACKET_COMPLETED_STATUSES` once, centrally. This is the intended product effect of (d), but it bites on day one.
- **R2 — `UNACCEPTABLE*` pass (D8).** Completion is not approval; an UNACCEPTABLE carrier can still be sent a rate con if someone books one. Decision for Main (one constant).
- **R3 — `mcpStatus` is hand-editable.** `CarrierForm` lets staff type `ACCEPTABLE` into a carrier that never completed a packet, defeating (d). Not changed here (would be a new rule: lock the field to sync-written values or turn it into a select). The audit row for each send should be enough to catch it: add `mcpStatus: standing.status` to the `SEND_RATE_CON` audit payload (Slice A does this — cheap, and it records which status admitted the send).
- **R4 — Demo/dev drift.** Already-seeded dev stacks keep the old vetted carrier row (idempotent seed) ⇒ P8 and manual demos refuse until reset+reseed or until `mcpStatus` is set. `devVerifyP.mjs` preflight turns this into a clear message.
- **R5 — Logo availability and format.** Only PNG/JPEG render; an SVG/WebP `logoKey` silently falls back to text (by design — the Company page upload does not restrict file type, so a user may not notice). If no Division on dev/prod has a `logoKey` yet nothing changes visually. The 5 s fetch timeout adds up to 5 s to Preview/Send when S3 is slow. Browser `fetch` relies on the existing bucket CORS GET rule (`backend.ts` L3186); a deploy that drops it would degrade every logo to text, not break sends.
- **R6 — `Division` ≠ `OwnershipDivision`.** The logo is `Division.logoKey` reached through `Load.divisionKey` (the entity that already supplies legal name/MC/remit). A load with no `divisionKey` has `division = null` and gets the text header `Broker` exactly as today; `OwnershipDivision` (revenue-division tag) has no logo field and is not used.
- **R7 — Sender cc is a behaviour change visible to carriers.** The carrier now sees the dispatcher's address on Cc (they were already replying to the tracking inbox via Reply-To). The audit row records `cc` and `senderCc`. Sender dedupe against `to` means a person who is both sender and a `to` recipient is not mailed twice.
- **R8 — Deploy shape.** No schema, no env, no IAM in this plan ⇒ Lambda code + front-end only. It still shares the one S2 deploy (brief: no doc-only or split deploys; wait for the previous Amplify job to finish before pushing). If S2 carries a schema change the combined deploy is a data deploy — not caused by this plan.
- **R9 — One-click paths have no picker.** Suggestion/offer sends still go to the default recipients; users who need a different address use the panel. Intentional (D6/D12).
- **R10 — Out of scope, stays out.** Multi-carrier covering; changing booking gates; adding `mcpPacketCompletedAt`/`mcpReviewStatus` to the schema; re-gating signing.
