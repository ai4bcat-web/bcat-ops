**The invariants K keeps, with the test that proves each.** (1) **The release gate is the only door into AR** (`src/lib/releaseGate.ts:143, 216`; enforced at `tms-shipment-actions/documents.ts:842-871`, `handler.ts` `SET_AR_STATUS`, `tms-finance-actions/invoices.ts`, `factor.ts`). The agent Lambda gets **no write grant on Shipment, Order, Load, LoadCarrier, Invoice, CarrierBill or FactoringItem** and no `lambda:InvokeFunction` on any router; a Retry on the Errors tab calls the owning router from the browser with the caller's own token — there is no path from a run to `arStatus`. (2) **A Shipment is the only record and `CREATE_SHIPMENT` the only creation door** (`handler.ts:1595-1602`). The tender agent's last machine step is a *proposal*; CREATE_TENDER on the trace is the human's `CREATE_SHIPMENT` (through `NewShipmentDialog`, the IntakePage precedent) — the run links to the shipment afterwards. (3) **A PRO is claimed, never checked; Void is the only exit.** The agent never passes `pro`; it puts the broker's reference in `tmsId` exactly as `NewShipmentDialog.tsx:310-313` already insists; nothing in K issues a DynamoDB `Delete` (`WorkflowRun` disables `delete`; a run is DISMISSED or RESOLVED). (4) **Unresolved customer is refused before the gate, never instead of it** (`customerResolution.ts:29-31`, the `DRAFT`-is-not-unresolved rule in `types/tms.ts:725-727`). The unknown-customer dialog is `SET_SHIPMENT_CUSTOMER` (`handler.ts:3249-3323`) and nothing else; it never creates a Customer. (5) **New models disable subscriptions, are read-only to clients, written only by a Lambda.** `WorkflowRun` is written only by `workflow-agent`; "Live while running" is a 3 s poll, not a subscription (the `useIntegrations` shape, `src/hooks/useIntegrations.ts:14`). (6) **Money is integer cents**: `proposal.billedCents`, `proposal.amountCents`; the AP extractor's `amountDollars` is converted once in `apProposal.ts` with the same `Math.round(x*100)` `merge.ts` uses today — no float crosses a boundary. (7) **Dev only, additive, byte-argued** (Schema below). (8) **COMPLETED ≠ approved** (spec `:382` security line): a run's `status` says the machine finished; `outcome PROPOSED` says a person has not acted; nothing consequential happens on COMPLETED.

**Judgement calls.** (1) **One new Lambda, `workflow-agent`, which replaces `vendor-ap-extract`.** The agent needs 90 s and 1 GB (a multi-page tender PDF through Sonnet is 20–40 s; `vendor-ap-extract/resource.ts:13-14` already sized this), is invoked by four kinds of caller (AppSync mutation, Lambda event, Function URL, EventBridge for the retry sweep) and holds the one secret the routers do not. Folding it into `tmsShipmentActions` (60 s, AppSync-bound, no Anthropic key) or `tmsDirectoryActions` (30 s) would make every quote-desk click wait behind a model call. Rejected: a `WorkflowStep` model — steps are ≤ 12 per run and live on the row as `steps: json` (the `Integration.events ≤ 50` and `Quote.events` precedent), so a trace is one read; a `WorkflowDocument` model — documents are pointers to keys the bridges already wrote, kept as `documents: json`, "pointed at rather than copied" (`NewShipmentDialog.tsx:310`). (2) **The agent proposes; a person applies, through the existing door, with their own identity.** Rejected: the agent calling `CREATE_SHIPMENT` by `lambda:Invoke` with a forwarded identity — same door in letter, but it hands a Lambda the ability to mint shipments and claim PROs with a synthesised caller, and the one structural guarantee worth having is that `workflow-agent` *cannot* create freight by any path. Rejected: auto-creating `TENDER_PENDING` rows (MVMNT does) — a shipment number and a PRO claim are forever, and a mis-classified spam e-mail would burn both; `TENDER_PENDING` is still where an applied tender lands, so Accept/Reject stays the review. The cost is one click per tender, which `IntakePage` already charges. (3) **`CREATE_SHIPMENT` gains `source: 'TENDER'`.** `Shipment.source` already lists `TENDER` (`resource.ts:1282`) and `CREATE_SOURCES` deliberately excluded it (`handler.ts:1448-1449`) because nothing produced one; K does, so the enum gains the value, the created status becomes `TENDER_PENDING` for that source, and `tenderRespond` finally has rows to act on. (4) **Three GSIs, argued.** `WorkflowRun` grows forever (every e-mail, every webhook); a scan-backed "last 200 runs" would cost the whole table per page view within a year. `byAgent` (`agent` × `updatedAt`) makes the per-agent list one query and "all" four merged; `byShipment` (`shipmentId` × `updatedAt`) is the shipment's AI Agent tab and the "when runs are linked" test; `exceptionOpen` (sparse `'OPEN'` × `updatedAt`, the `Load.checkCallOpen` precedent, `resource.ts:116-118, 179`) is the Errors queue — without it an unresolved failure older than 200 runs silently leaves the queue, which is a bug in a queue. Rejected: a single `bucket='RUN'` partition (hot-key anti-pattern and still no exception query); `shipmentId` only (no run list). Drop order if the measured cost exceeds the ceiling: `exceptionOpen` first (fall back to `byAgent` × FAILED, documented limit), then `byShipment` (fall back to `byAgent` filtered client-side). (5) **Memory lives on the records that own the party, and on `TmsSettings` for the org.** `TmsSettings.aiAgents: json` and `Customer.aiMemory` / `Carrier.aiMemory` (`json`, written by `SAVE_SETTINGS`, `UPSERT_CUSTOMER`, `UPSERT_CARRIER` — the routers that already own those rows) rather than a `Memory` model: a memory card is one Markdown string with a revision, edited by a person, read by the agent, and the party's profile page is where the spec puts it (`:382`). The agent **reads** memory and stamps the revisions it read on the run; it never writes memory — a feedback note is saved on the run (`feedback: json`) and a person folds it into the card. Rejected: agent-written memory ("learned" rules nobody reviewed, on a record the gates read). Vendor memory waits for a Vendor record: `VendorPayable.vendor` is a string (`resource.ts:2783`) and there is no Vendor model. (6) **Sender identifies the party, from fields that exist.** `partyMatch.ts` resolves the From address against `Customer.contacts[].email` (`resource.ts:891`), `Carrier.email` (`:2528`) and `CarrierContact.email` (`:2573`), then the sender domain (freemail domains excluded) against the same, then the display name / signature through `findCustomerMatches` (`tmsDirectory.ts:74`, the same normaliser the directory dedupes on). An exact e-mail hit sets `partyId`; a domain or name hit sets `partyCandidates` and the run ends `UNKNOWN_PARTY` for a person to pick — the `TenderPrefill.customerId` rule (`intakeTender.ts:49-54`, "its absence means a human still has to pick the customer, which is the correct outcome"). No contact is ever created by the agent (spec says "may be"; here the Apply dialog offers it, by the human, through `UPSERT_CUSTOMER`/`UPSERT_CONTACT`). (7) **Unknown customer is one rule, in one place.** The Errors tab's "unknown customers" are exactly `isCustomerUnresolved(shipment)` over the working set, not voided, not CANCELED — the predicate the board (`ShipmentsBoard.tsx:453`), the detail (`ShipmentDetail.tsx:113`), the AR worklist (`useArWorklist.ts:116`) and every router refusal already share; the dialog is the detail's `UnresolvedCustomerCard` (`ShipmentDetail.tsx:479-541`) lifted into its own file and wrapped in a `TmsDialog`, calling `setShipmentCustomer` (`apiClient.ts:1814`). Rejected: a second "unknown" test on the run (`UNKNOWN_PARTY`) feeding the same list — a run with no party and no shipment is an AI-agent row, and once a person applies it with typed text it becomes a shipment row; the two never double-count because a run's exception closes on apply. (8) **Retry is the owning action, and only where the owner has one.** AI → `RETRY_WORKFLOW_RUN` (a new attempt on the same row, replayed from the stored source, refused once `outcome APPLIED`); tracking → the existing `SEND_TRACKING_LINK` / `TEXT_DRIVER` / `LOG_CHECK_CALL` dialogs; integration health → `VALIDATE_INTEGRATION`; accounting sync → **no Retry**, because J's QBO `sync` is a stub and there is nothing to retry (the row says "Preview only until live sync"); unknown customer and EDI → none, as the spec says. The Workflows page owns no Lambda action for any retry but its own. (9) **The shared tracking toggles get their first reader.** J stored `trackingIntervalMin`/`trackingDurationHours` and said nothing reads them; the Errors tab's "no ping" rule reads `trackingIntervalMin × 3` against `TrackingLink.lastPingAt` (`resource.ts:1906`) on ACTIVE CARRIER_PING links of in-transit loads. Rejected: inventing a tracking-error field on Load. (10) **The Workflows page stays under `page-tms` with role-shaped defaults, not role-shaped refusals.** Role groups exist as `role-<ROLE>` (`roles.ts:127`, ROLES `:30-38`: ADMIN, MANAGER, CUSTOMER_REP, CARRIER_REP, AR_AP, COMPLIANCE) and the client sees them (`AuthContext.tsx:19`); the spec's matrix (`:380`) is the tab's **default** integration filter per role, widenable by chip — a carrier rep who needs to see an unknown-customer row is not refused by a filter. Integration-health rows need `LIST_INTEGRATIONS` (owner/ADMIN, `tms-directory-actions/handler.ts:158` via J); for everyone else those counts read 0 with a hint, the `canSeeIntegrations` rule the shipment detail already applies (`ShipmentDetail.tsx:86-90`).

## Schema (`amplify/data/resource.ts`, additive)
