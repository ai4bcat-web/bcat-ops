# Step F — AR: invoicing & payments (dev)

## Architecture and scope

Planned by Claude Fable (`plan`, planning-only, as in A–E). Sources: `MVMNT_TMS_SPEC.md` §3.1, §3.6, §6.2 (`Invoice`, `PaymentGroup`, `CreditMemo`), §6.6, §7 row F; `TMS_DESIGN.md` §4.11, §4.12, §5, §6; `TMS_BUILD_BRIEF.md` hard rules; every file cited below re-read in the working tree. F adds **two new models** — **Invoice** (one issued bill for one order: line snapshot, balance, PDF) and **ArPayment** (every cash receipt, credit memo, write-off and reversal, with its allocations) — one new router **`tmsFinanceActions`** behind a new `invoicing` page key, additive fields on `Order`, `FactoringItem`, `TmsSettings`, `ShipmentNotice`, one GSI on `Order`, the storage prefix `invoices/*`, an additive document lookup in `otr-actions`, an `/ar` page, an AR card on the shipment, an AR tab on the customer and a settings card. New models `allow.authenticated().to(['read'])`, subscriptions disabled, Lambda-written.

**The status machine.** `Order.arStatus` already carries the ladder (`resource.ts:1113-1118`); B writes DOCS_NEEDED, E's `READY_TO_INVOICE` performs DOCS_NEEDED → UNBILLED behind the document gate (`tms-shipment-actions/documents.ts:772-838`), `SET_AR_STATUS` hand-sets the three non-money values (`handler.ts:3711-3748`, `AR_STATUSES_WRITABLE` `:304`). F adds two transitions and one writer: **UNBILLED → UNPAID happens only inside `GENERATE_INVOICE`**, in the `TransactWriteItems` that puts the `Invoice` row and freezes the order's `LoadFinancials` (`frozenAt`, `resource.ts:1261-1263` — every charge-writing action already refuses after it, `handler.ts:1320, 2240, 2500, 2752, 3172, 3429`); **UNPAID → PAID happens only inside `RECORD_PAYMENT`** (or `WRITE_OFF`) when the transaction leaves `Invoice.balanceCents` at 0; `VOID_INVOICE` is the only way back (UNPAID → UNBILLED, `invoiceId` cleared, financials unfrozen, the Invoice row kept as VOID). No date, number match, OTR status or stream event writes UNPAID or PAID. An **invoice record** is an immutable snapshot of the order's CUSTOMER `LoadCharge` lines (`resource.ts:1272-1293`), bill-to, remit-to, terms and due date, never re-read from the charges. A **payment** is a row with `applications[{invoiceId, amountCents}]` and `creditApplications[{paymentId, amountCents}]`; a **credit memo** is an `ArPayment` of kind CREDIT_MEMO whose `unappliedCents` is spent only through a later payment (spec §6.6 "applied only through a payment"); an overpayment is the paying row's own `unappliedCents`, a credit without a second model. A mistaken payment is reversed by a REVERSAL row, never edited (`TMS_DESIGN` §4.11). **AR aging** is a pure function over the open invoices read from one sparse index, never from orders.

**Judgement calls.** (1) **A finance router, not more shipment actions.** `tmsShipmentActions.authorize` admits anyone with `page-loads` (`handler.ts:419-430`) and the file is 4,185 lines; posting money gets `tms-finance-actions` (`tmsFinanceActions(action, input): AWSJSON`), gated to owner / ADMIN / `page-invoicing`, posting actions ADMIN-only by default — the `vendor-ap-actions` precedent `TMS_DESIGN` §6 names, reusing `_shared/shipmentStore.ts`. (2) **One invoice = one order.** `Order.invoiceId` is one string (`resource.ts:1116`); MVMNT's batch generates one invoice per order and sends one e-mail per customer + bill-to (spec §6.6). Consolidated invoices were rejected: an `InvoiceLine` table under the CloudFormation resolver cap and a 40-order transaction, for a flow MVMNT does not show. With one order per invoice the payment transaction is 1 payment + N invoices + N orders + K credits + 1 audit — **≤ 40 invoices and 10 credits per payment**. (3) **The invoice PDF is rendered server-side with `pdf-lib`.** E kept jsPDF in the browser because nothing in E generated unattended; F does — Batch generate makes up to 25 PDFs in one call, `EMAIL_INVOICE` must attach the exact bytes it stored, a regenerate cannot wait for a browser. `pdf-lib` is already bundled in Lambdas (`_shared/asciiSafePdf.ts:20`, `pod-actions/podCheck.ts:16`) and already draws text pages in `src/lib` (`filePacketPdf.ts:11`); it is isomorphic, so the **same** `buildInvoicePdf` renders the dialog preview in the browser and the stored file in the Lambda. Cost: no `jspdf-autotable` — `invoicePdf.ts` lays out its own table. Rejected: jsPDF + `SAVE_GENERATED_DOCUMENT {pdfBase64}` (`documents.ts:426-447`), a browser loop for a batch and a second upload for the e-mail. (4) **Invoice bytes live under `invoices/{customerId}/{number}-v{n}.pdf`, not as a `ShipmentDocument` row.** `tmsShipmentActions` is that model's single writer (`backend.ts:1798`) and an INVOICE row would flow through `recacheDocGates`; the Documents tab lists the invoice as a **derived** line from `Order.invoiceId`, as it derives the rate con from `LoadCarrier.rateConKey` (E judgement 1). (5) **Payments, credits, write-offs and reversals are one model.** Four tables would each need a customer index; one row kind plus `unappliedCents` covers the Credits board, "apply available credits" and the overpayment checkbox. MVMNT's editable payment rows are rejected: posted ledgers are immutable, no user delete (`TMS_DESIGN` §6). (6) **Aging never scans orders.** `Invoice.arOpen` is a sparse `'OPEN'` carried while ISSUED or PARTIAL and **removed** (`REMOVE`, never nulled — Step C's `Type mismatch … Actual: NULL`, `BUILD_LOG` `32d3eec`) on PAID/VOID; one query of `arOpen` + `dueAt` is the open book; the customer tab and `oldestOpenInvoiceDays` read `customerId` + `issuedAt`; the Paid tab reads `invoiceMonth` + `issuedAt`. The board's `listOrders()` per poll (`useShipments.ts:79`) is not repeated: the worklists come off the new `Order` index. (7) **Send to Factor writes the queue row the intake e-mail would have written; the existing `submit` does the rest.** `FactoringItem.id` is the PRO and `findLoadByPro` matches `Load.aljexId` (`otr-actions/handler.ts:130-145`); a shipment-born load's `aljexId` **is** its `loadNumber` (`handler.ts:878`), so a row with `id = load.aljexId` resolves with no change to `resolve`/`assemble`. `SEND_TO_FACTOR` puts that row, links it to the invoice and stops; a person presses **Submit** — on `/factoring` or the AR card — which calls the unchanged `manageOtr submit` (`otrClient.ts:119`). Rejected: a second OTR client, and auto-submit (`backend.ts:2404-2407`: human-initiated only). (8) **A factored invoice stays open until a person records a payment.** OTR's advance is financing (`TMS_DESIGN` §4.12); the hourly sync mirrors `otrStatus` onto the row, the card shows it, and on a terminal status offers **Record factor payment** (method FACTOR, reference `otrInvoiceId`) — a click, never a cron. (9) **Legacy orders leave AR through a new `arStatus` value, `LEGACY`.** The backfill left 890 orders in DOCS_NEEDED/UNBILLED (`handler.ts:3901`) whose invoices went out through Aljex and OTR; they would be the whole To-invoice tab. Additive enum values are the E precedent (`TrackingLink.kind` `+ CARRIER_UPLOAD`, `resource.ts:1368`). A LEGACY order is never a worklist row and its credit exposure falls back to the load rule it had before B, so no customer's number moves.

**Corrections to the brief/spec from the code.** "Send to Factor via the existing OTR flow" means less and more than it reads. Less: every OTR field is **typed on the queue row** (`otrManualFields`) — `buildReadiness` passes `load: {}` and says why (`otr-actions/handler.ts:466-477, 494-511`); nothing comes from the load, its Locations or the Customer. F prefills those typed fields from the **issued invoice snapshot** (InvoiceNo = our number, InvoiceAmount, PoNumber from the CUSTOMER|ALL `PO` reference, BrokerMC from `Customer.mcNumber` `resource.ts:757`, From/To city-state-ZIP from the first pickup and last delivery) because an issued invoice is human-reviewed, not a guess; every field stays editable on the row. More: OTR reads a POD only from `PodDocument` / `DriverSubmission` and a rate con only from `Load.rateConfirmKey` / a submission (`findPod` `:426-428`, `findRatecon` `:438-452`), so a POD the carrier sent through E's portal is invisible to it; F adds a last-resort `ShipmentDocument` lookup to both, after the own-fleet stores. Nothing OTR can be proven on dev: the OTR secrets are neutered there (`backend.ts:2576`) against a **production** base URL (`:2421`) — F proves the row, its readiness and its refusals; `submit` is proven on main. `FactoringItem` is the one finance model the client may `create`/`update` (`resource.ts:1800`); F leaves that alone (the own-fleet queue writes status directly, `apiClient.ts:813-822`) and writes TMS rows from the Lambda. The brief's gate "docs + references + $0" is one-third built: `READY_TO_INVOICE` checks documents only (`documents.ts:772-838`), references are checked at save (`handler.ts:1239, 1287`), nothing checks revenue > 0 — `invoiceReadiness` re-checks all three at generation. `SET_AR_STATUS` checks only the *requested* status, so it can move an invoiced UNPAID order back to DOCS_NEEDED (`handler.ts:3711-3748`); F adds one refusal: `invoiceId` set → "void the invoice first". `Order.invoiceEarly` gates both UNBILLED paths (`handler.ts:3726`, `documents.ts:786`) and `SAVE_ORDER_FORM` accepts it (`:1374`), but no screen sets it (`apiClient.ts:1346` only reads it) — F adds the toggle. `TmsSettings.invoiceNumberFormat` is a free string with no tokens (`resource.ts:925`); F defines `{prefix}` `{yyyy}` `{n}` / `{n:6}`. `arUnbilledStage` is `a.string()` "label for the UNBILLED AR stage" (`:953`) but `boolean | null` in `src/types/tms.ts:310` and unread; F does not build the stage-skip. The own remit-to is per Division (`resource.ts:905-908`, printed by `carrierRateCon.ts:130-139`); a **factor** remit-to exists nowhere (grep `remitTo`), so "remit-to switches on the factor flag" needs `TmsSettings.factorRemitTo`. Credit exposure is computed two ways: the Lambda from orders + shipments (`handler.ts:770-784`; UNPAID → INVOICED, `customerCredit.ts:146-153`), the profile from **loads only** (`CustomerProfile.tsx:103-106` → `creditExposureForCustomer`), which has no paid state — an order F marks PAID would still count there; F points the profile at `creditExposure` and caches `Order.arBalanceCents` so a half-paid invoice exposes its balance. `oldestOpenInvoiceDays` / `INVOICE_PAST_MAX_DAYS_LATE` are implemented (`customerCredit.ts:270-275`) and never fed (`handler.ts:784`); F feeds them from the customer's open invoices. Amplify's `createdAt` cannot be a GSI sort key (`resource.ts:1456, 1495`): every new index sorts on an own timestamp. `ShipmentNotice` already has two writers through `_shared/shipmentNotices.ts` (`tmsTrackingActions`; `shipment-notifier` with its own SES grant, `backend.ts:2177-2179`), so a third is the pattern. SES is denied on dev (`backend.ts:2578-2581`): every invoice e-mail lands NOT_SENT with copyable text and 1-hour download links, as `EMAIL_DOCUMENTS` does (`tms-tracking-actions/handler.ts:1760-1785`). `Load.rate` mirrors order revenue (`handler.ts:3188-3197`), so settlements and the dashboard's factoring card keep reading the invoiced amount unchanged. **Deferred:** AP, carrier bills, remittance (G); QuickBooks sync and HaulPay/Denim/Triumph (J — OTR is the only factor); statements and dunning; multi-currency; portal invoice view; commission triggers on PAID (I).
