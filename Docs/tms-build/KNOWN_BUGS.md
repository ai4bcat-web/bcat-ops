# Known bugs

## Fixed on a branch, awaiting deploy

### Empty rollup rows painted as zeros (2026-11-08, branch `fix/rollup-empty-legacy`)
Rollup rows computed from an empty Shipment table (36 `LG:` rows `{v:1,days:{}}`, `sourceCounts {shipments:0}`) were treated as usable, so the legacy `/dashboard` showed zero revenue/loads against live costs. Fixed: readers treat empty-source / no-days rows as unusable (exact path) and the `tms-dashboard-rollup` Lambda no longer writes them. Needs a Lambda and a frontend deploy. See BUILD_LOG.md.

## Open (logged, NOT fixed)

### TMS defaults card save fails with "expectedUpdatedAt is required" when the row was created after the page loaded
- **Card:** "TMS defaults" (`src/features/settings/TmsSettingsCard.tsx`). The same pattern is in every settings card/page that saves `TmsSettings` (`TeamsCard`, `ChargeCodesCard`, `ConsolidationCard`, `CarrierDocumentsCard`, `CustomerSettingsCard`, `PostalCodeAliasesCard`, `UsersRolesCard`, `BillingPage`, `BrandingPage`, `NotificationsPage`, `AiAgentsPage`, `DirectoryPages` org defaults, `DivisionsPage`).
- **Code path:** on mount the card calls `getTmsSettings()` and stores the result; when the `TmsSettings` row does not exist yet, it gets `null` (`settings` stays null). Save calls `saveTmsSettings(patch, settings?.updatedAt ?? undefined)` (`src/lib/apiClient.ts`), which sends `expectedUpdatedAt: undefined` in the `SAVE_SETTINGS` directory action. In `amplify/functions/tms-directory-actions/handler.ts` `saveSettings` re-reads the row: if it is missing it creates it (no CAS needed); if it NOW exists (another admin, another card, or `ApptsPage`'s `saveTmsSettings({ autoClearPastAppts })` created it after this page loaded) it calls `assertExpectedUpdatedAt(input)`, and `assertDefined` throws `expectedUpdatedAt is required`. The page also never updates its `updatedAt` after another editor's write, so even a non-null stale value would fail with the CAS mismatch instead.
- **Root cause:** the client's optimistic-concurrency token is captured once at first load; a null token means "row did not exist", but the server requires a token as soon as the row exists, and the card never refetches.
- **Proposed minimal fix:** in `saveTmsSettings` (single choke point), on that specific error (`/expectedUpdatedAt is required/`, or the CAS-conflict error for a stale token) call `getTmsSettings()`, and retry the save ONCE with the row's current `updatedAt`, only when the caller's patch is a partial patch of fields it owns (the server already keeps unmentioned fields). Then the card's `setSettings(updated)` refreshes its token. Alternative: send the row's current `updatedAt` by refetching right before save in each card. Do not retry more than once, and surface the error otherwise so a real conflict is still reported.

### LG rows only count loads that have a Shipment
Legacy rollup rows (`LG:<month>`) are computed from Shipments joined to their Loads. Until the production backfill (Shipment rows for old loads) has run, a partly-backfilled month can understate the legacy dashboard. The new rule (no-days or empty-source row is unusable) covers only the completely empty case, not a partial one. Recommendation: run the Shipment backfill and the rollup backfill together, using the manual door `{ backfill: { from, to } }` on `tms-dashboard-rollup` after the Shipment backfill completes (the sweep alone will not recompute a non-empty row that is merely stale in content until a source write dirties it).
