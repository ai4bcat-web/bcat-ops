# Step D — Tracking & check calls (dev)

## Architecture and scope

Planned by Claude Fable (`reviewer`, planning-only, as in A/B/C). Sources: `MVMNT_TMS_SPEC.md` §3.4, §6.1 (`LoadCheckCallIncidentType`, `NEXT_CHECK_CALL_DUE/OVERDUE`), §6.2 `LoadCheckCall`, §6.5, §7 row D; `TMS_DESIGN.md` §4.7, §4.16, Phase 8; `TMS_BUILD_BRIEF.md` hard rules. Two new models — **LoadCheckCall** (the per-load event log: manual check calls, driver-app stop events, SMS-link pings, dispatch/ETA/incident rows) and **TrackingLink** (tokenised public links: the carrier-driver ping link and the per-shipment Customer Link) — plus additive fields on `Load`, `LoadCarrier`, `Shipment`, `TmsSettings`. New models `allow.authenticated().to(['read'])`, subscriptions disabled, Lambda-written. Timestamps ISO; incident money is `LoadCharge` lines in cents. D builds on what B/C already put down: `Load.trackingProvider` NONE·MANUAL·LINK·DRIVER_APP·MOTIVE, `Load.nextCheckCallAt/nextCheckCallNote/checkCallOpen` with the sparse `checkCallOpen`+`nextCheckCallAt` GSI (the worklist), `Load.statusSource CHECK_CALL|DRIVER_APP`, `LoadCarrier.dispatchedAt/driverPhone/truckId/pickupEtaAt/deliveryEtaAt`, `DISPATCH_LOAD`'s next-check-call fields, `canTransitionLoadStatus`/`loadStatusFromStopTimes` in `src/lib/shipmentStatus.ts`, `RECALC_CHARGES` for sided charge lines.

**Judgement calls.** (1) **`tracking-api`: extend, not replace.** The existing Function URL (`amplify/functions/tracking-api/handler.ts`, `GET /t/<code>`) is truck-centric — the code is `Equipment.trackingCode`, it answers for own trucks only, CORS is GET-only. The customer link is shipment-centric and the carrier link needs a POST, so they are new routes on the same Lambda (`GET /s/<token>`, `GET /l/<token>`, `POST /l/<token>/ping`, CORS widened to GET+POST); `/t/<code>` and `src/features/tracking/TrackPage.tsx` are untouched. One public Lambda, one role, one `PORTAL_ORIGINS` pin, still outside `previewCallable`; `TMS_DESIGN`'s separate `tracking-link-api` is folded in. (2) **One timeline, driver app contract frozen.** `/paperwork/stop-event` (`driver-app-api/handler.ts:2971-3050`) writes only `stops[].arrivedAt/departedAt` by SDK `UpdateCommand` — `Load.status` is never set, so B's `statusSource DRIVER_APP` has no writer today. D adds a Load-stream consumer `load-tracking-projector` that turns a newly stamped stop time into a `LoadCheckCall` row with the deterministic id `evt:<loadId>:<stopId>:<ARRIVED|DEPARTED>` (conditional Put) and advances `Load.status` through `loadStatusFromStopTimes`. Every staff path that stamps a time (`UPDATE_STOP SET_TIMES`, `LOG_CHECK_CALL`) writes the same id first, so the first writer wins and nothing is counted twice; POD-close and dispatch-MMS auto-POD stamps (the other writers of `stops[]`) are caught by the same projector. Motive positions are **not** copied into check calls (`TMS_DESIGN` §4.16 said `CheckCall{source: MOTIVE}`; six fixes an hour per truck would swamp the table): the Tracking tab reads `TruckLocationHistory` by its `(truckId, locatedAt)` key for the load's window and `buildTimeline()` merges the sources in memory. (3) **Status from check calls** goes through the stop clock, not a second table: ARRIVED/DEPARTED stamp the stop (never overwriting an existing stamp) and `loadStatusFromStopTimes` yields LOADING / IN_TRANSIT / UNLOADING / DELIVERED — first pickup and last delivery only, intermediate stops change nothing, never backwards, CANCELED stays. No other event type moves status; `statusSource` is `CHECK_CALL` (manual) or `DRIVER_APP` (projector). (4) **Due/overdue** follows `dispatch-nudge` — `schedule: 'every 5m'` in `defineFunction`, Slack DM via its `dm()` helper — but as its own `check-call-notifier`: `dispatch-nudge` is driver-centric and wired to the dispatch tables and SSM. The in-app worklist (`/check-calls` + nav badge) polls the existing GSI and works on dev, where every schedule is disabled. (5) **SMS reuses the dispatch Twilio path**: `_shared/dispatchSend.sendDispatchText` into a `DispatchConversation` for the driver's phone (the `ratecon-assigned-text` precedent), so the text and any reply live in Dispatch. Dev has no `/bcat/dispatch/<poolId>/` config, so the action returns `smsStatus 'NOT_CONFIGURED'` with the URL for Copy link.

**Corrections to the brief/spec from the code.** Dev cannot prove notifications, SMS or e-mail end-to-end: `backend.ts` disables every `CfnRule`, denies `ses:*`, leaves Twilio unconfigured and creates both Load-stream mappings disabled — D's actions degrade to in-app + copy-link, the notifier is invoked by hand on dev, and the projector is the one stream consumer deliberately **enabled on dev** (`enabled: BCAT_ISOLATED_PREVIEW !== 'true'`) because it writes only our own tables. `TMS_DESIGN` Phase 8's Google map is not in D; `FleetMiniMap` (SVG, already behind `/track/:code`) draws positions. `appt-need-notifier` is a stream consumer, not a schedule. `rederiveShipmentStatus`/`readBundle`/`shipmentMirrors`/`buildSearchKey` are private to `tms-shipment-actions/handler.ts`; D moves them verbatim to `amplify/functions/_shared/shipmentStore.ts` so the projector runs the same derivation (mechanical move, guarded by the existing handler tests). **Deferred:** geofence auto-status (stops carry no coordinates; `Location.lat/lng` do), background GPS (EZ Tracking is one ping per tap, same here), Trucker Tools/MacroPoint/Highway sessions (J), per-contact status e-mails (E), reverse geocoding of pings (`tmsGeocode` is forward-only), `TruckLocationHistory` TTL (runbook), an invoicing block on open incidents (F reads `Load.openIncidentCount`).

## Schema (`amplify/data/resource.ts`)

GSIs `shipmentId`, `loadId`.

**Load +**: `lastCheckCallAt`, `lastCheckCallType`, `lastKnownAt`, `lastKnownCity`, `lastKnownState`, `lastKnownLat`, `lastKnownLng`, `lastKnownSource` MANUAL·DRIVER_APP·LINK·MOTIVE·SYSTEM, `openIncidentCount`, `deliveredAt`, `checkCallDueNotifiedAt`, `checkCallOverdueNotifiedAt`. **LoadCarrier +**: `trackingLinkId` (the ACTIVE CARRIER_PING link), `trackingStartedAt`, `trackingStoppedAt`. **Shipment +**: `customerLinkId`, `customerLinkSentAt`. **TmsSettings +**: `checkCallDefaultIntervalHours` (4), `checkCallGraceMinutes` (15; DUE→OVERDUE), `checkCallNotifyChannel` IN_APP·SLACK·BOTH (BOTH), `checkCallSlackChannelId`, `trackingLinkExpiryHours` (72 after the last delivery appointment), `customerLinkExpiryDays` (14), `customerLinkShowsCarrier` (false), `customerLinkShowsPosition` (true), `trackingContact: json` `{mode: 'CUSTOMER_REP'|'FIXED', name?, email?, phone?}` (CUSTOMER_REP), `trackingSmsTemplate` (`{broker}: share your location for load {loadNumber} here: {url}`). **Secondary-index budget:** one new GSI per *existing* table per deploy. D adds **zero** GSIs to Load, LoadCarrier, Shipment and TmsSettings — the worklist rides B's `checkCallOpen`+`nextCheckCallAt`, Motive positions ride TruckLocationHistory's own key, tokens are primary keys on a new table. The five new GSIs (LoadCheckCall ×3, TrackingLink ×2) are on brand-new tables and unconstrained; every existing table's slot stays free for E.
