**Roles and teams.** The spec's roles are Admin, Manager, Customer Rep, Carrier Rep, AR/AP, Compliance plus per-user claims (`:288`, `:181`). The smallest additive move: **a role is data on `UserProfile`, and it is projected onto Cognito groups** — exactly as `withDerivedLegacy` mirrors a canonical field onto a legacy one (design `:112`). `setRole` writes `UserProfile.role`, then puts the user in `role-<ROLE>` and in the role's page groups from one table, `src/lib/roles.ts` `ROLE_PAGES` (ADMIN → the `ADMIN` group as today; MANAGER → every TMS key `loads · customers · carriers · locations · quotes · invoicing · carrierPay · reports · commissions · audit`; CUSTOMER_REP → `loads · customers · locations · quotes · invoicing · reports · commissions`; CARRIER_REP → `loads · carriers · locations · quotes · carrierPay · reports · commissions`; AR_AP → `invoicing · carrierPay · vendorAp · factoring · reports`; COMPLIANCE → `carriers · customers · locations`), and removes the page groups the previous role granted that the new one does not — **page grants outside any role's set are left alone** (the Drivers/Fleet/Finance/System keys, `navItems.ts:87-129`, are own-fleet work, not TMS roles, and stay per-user "additional permissions" as today). Nothing reads the profile to decide access: `hasPageAccess` and the five `authorize()`s keep reading the token, so a role change is a Cognito change and costs no table read per call. **What would break if roles stopped being groups** is precisely those six readers plus the token itself — groups ride in the ID/access token (`useAuth.ts:4-8`), so a Lambda deciding from a table would add a DynamoDB read to every action and the client a profile fetch before first paint; and a user whose token predates a change keeps the old groups until refresh (already true of page grants today — the Users page says so). **Claims** are the spec's "additional permissions" (`UserClaim`, `:181`) and land as `claim-<KEY>` groups, enforced only where an admin-only switch already exists: `CREDIT_LIMIT_EDIT` opens the credit fields (`tms-directory-actions/handler.ts:795-798`), `AR_POSTING` / `AP_POSTING` / `AP_APPROVAL` satisfy the three `…AdminOnly` flags (`tms-finance-actions/handler.ts:160-169`) — `flag !== false && !isAdmin && !groups.includes('claim-X')` — and `CARRIER_STATUS_EDIT` the status change in `tmsCarrierActions`; any other claim is recorded and not enforced, said so on the page. **Who may edit roles:** owner/ADMIN manage users (spec `:288` Admin; today owner only, `handler.ts:80-83`) — invite, role, teams, claims, pages, disable/enable, reinvite, force sign-out; **only the owner** grants or revokes ADMIN and deletes a user (`:146-166` kept). **Lock-out guards**, all in the Lambda: the owner's role is always ADMIN and no action may remove the owner from `ADMIN` or disable the owner; an ADMIN may not demote or disable themself; `setAdmin false`/`setRole` refuse when the target is the last enabled member of `ADMIN`; `OWNER_EMAIL` stays hard-coded in its five places (not a setting — a setting is editable by the people it protects against). **Teams** are `TmsSettings.teams: json` `Team[] {key, name, memberIds[], senderAddresses {shipment, rateCon, quoteReply, customerInvoice, remittance}, showContactOnTracking, active}` (spec `:287`'s five sender slots); `Customer.teamKey`/`Carrier.teamKey` become pickers over it, `UserProfile.teamKeys[]` is the membership mirror written by the same save. Sender addresses are **stored, not used** in I: SES is denied on dev and every sender today is `FROM_ADDRESS` (`store.ts:64`); J/L wire them. **Rep view limits** (`limitCustomerRepView`, `limitCarrierRepView`, spec `:287`) are board filters ("Mine" default on for reps, every row for managers/admins) and nothing more: every TMS model is `allow.authenticated().to(['read'])` (design Q16, `:427`), so a limit is a courtesy, not a boundary, and the Academy article says so.

**Commissions — whose numbers, on what event, at what rate, recorded where.** *Whose:* the spec's `CommissionRoleName`s (`:180`) resolve to people already on the records — PRIMARY/SECONDARY_ACCOUNT_OWNER = `Customer.accountOwnerIds[0]` / `[1..]` (`:837`), PRIMARY_OPERATED_BY = `Customer.operatedById` (`:836`), CREATED_BY = `Order.createdBy` (`:1175`), CARRIER_BOOKING_REP = the ACTIVE|TONU `LoadCarrier.carrierRepId` (`:1212`), PRIMARY_CARRIER_REP = `Load.carrierRepId` (`:101`), MANAGER = the rep's `UserProfile.managerId`, SPECIFIC_USER = named on the role; the customer rep of the order (`Order.customerRepId`, `:1128`) is the ACCOUNT_OWNER fallback when the customer names none. *On what event:* **never before the money is frozen.** `GENERATE_INVOICE` stamps `LoadFinancials.frozenAt` in its transaction (`invoices.ts:394-402`; `RECALC_CHARGES` refused after it, `resource.ts:1331-1332`), and the carrier side is final only at `LoadCarrier.chargesFinalizedAt` (G: `UPDATE_CARRIER_CHARGES` allowed after `frozenAt`, refused after finalization). So `commissionTrigger` offers **GENERATE_INVOICE** (default) and **INVOICE_PAID** (`recordPayment` settles the order, `payments.ts:180-181, 214-215`); the spec's READY_TO_INVOICE (`:180`, `:289`) is **not offered** — at UNBILLED (`tms-shipment-actions/handler.ts:4173-4188`) nothing is frozen and a commission on a number that can still change is a number that will be wrong. *At what rate:* a plan resolved in the spec's priority — user → customer → team → the single default plan (`:289`) — by the pure `resolvePlan`; each role is FIXED `rateCents`, PERCENT_REVENUE or PERCENT_PROFIT `rateBps`, with optional **per-load** tiers (by margin bps or profit cents, graduated or straight); period tiers (Period Sum / Average, `:289`) are deferred — they need the period closed before any row is final, which is the pay-period step's job, not the trigger's. *Basis, in integer cents:* `revenueCents = Invoice.totalCents − Invoice.writtenOffCents` (`resource.ts:1406-1408`; a credit memo is kept cash, not reduced revenue — F's model, `:1446-1449`), `costCents = Σ LoadFinancials.costCents` over the order's loads (`:1326`), `profitCents = revenue − cost`; **`amountCents = roundHalfAwayFromZero(basisCents × rateBps / 10000)`**, computed once per role; secondary roles split the role amount by `splitBps` with a largest-remainder allocation so Σ shares = the role amount; a FIXED role is `rateCents` once per order; **`Math.round` is not used on a value that can be negative** (it rounds −2.5 to −2). *Own fleet:* an OWN_ASSET leg carries `costCents: 0` (G plan, `ASSIGN_ASSET`), so PERCENT_PROFIT would pay a rep on a 100 % margin; the row is written with `basisNote 'OWN_FLEET_NO_COST'`, `amountCents 0` and `needsReview: true` under a PERCENT_PROFIT role, and normally under PERCENT_REVENUE/FIXED — no cost is invented. *Recorded where:* a **Commission** row per order × role × rep with a deterministic id `cm:<orderId>:<roleName>:<repId>`, written only by `tmsFinanceActions` (`commissions.ts`). **The recomputation rule** is one function, `RUN_COMMISSIONS {invoiceId | month}`: it computes the set of rows an invoice should have today and reconciles — a missing row is Put (`attribute_not_exists(id)`), an **UN_APPROVED** row that differs is rewritten in place under CAS on `version` with `source RERUN`, a row at **MANAGER_APPROVED or later** is never touched and the difference becomes an **ADJUSTMENT** row (`kind ADJUSTMENT`, `adjustsId`, signed `amountCents`, UN_APPROVED, its own deterministic id `cma:<orderId>:<roleName>:<repId>:<n>`). Every money move calls it after its own transaction, best-effort like `storePdf` (`invoices.ts:405-411`): `GENERATE_INVOICE`, `RECORD_PAYMENT` when settled (INVOICE_PAID trigger), `WRITE_OFF` (basis falls), `RECORD_BILL` / `APPROVE_BILL` (cost moves; `UPDATE_CARRIER_CHARGES` lives in the shipment router, which invokes nothing — the page's "Recompute" and the pay-period submit cover that path, and `costFinal` on the row shows when every assignment is finalized or OWN_ASSET). **`VOID_INVOICE`** is the exception and runs **inside** its transaction (`invoices.ts:677-731`): UN_APPROVED rows → CANCELLED; approved or paid rows get a **REVERSAL** row with the negated amount — the ledger rule F and G already keep (`resource.ts:1447-1449`, `:1558-1559`). A re-price after freeze is impossible, so there is no case the rule does not cover. *Approval and pay:* status ladder `UN_APPROVED → REP_COUNTERED | MANAGER_COUNTERED | MANAGER_APPROVED → FULLY_APPROVED → PAID` (`:180`), `CANCELLED` from any unpaid rung; `OVERRIDE_COMMISSION {amountCents, note}` (manager/admin) on an unapproved row keeps `amountCents` and writes `overrideCents` — the computed number is never erased; pay periods come from `commissionPaySchedule` and `SUBMIT_PAY_PERIOD` stamps `payPeriodId` on every FULLY_APPROVED row whose `triggerAt` falls in the window, in batches of ≤ 90 (design `:400`), `APPROVE_PAY_PERIOD` and `PAY_PAY_PERIOD {paidAt, reference}` are admin; a statement PDF per rep per period via pdf-lib (`invoicePdf` precedent), stored under `commissions/<repId>/<periodId>.pdf`. **No money leaves through this**: a paid period is a record that payroll happened elsewhere, like `MARK_SENT`.

**Judgement calls.** (1) **No new Lambda.** Every router is `resourceGroupName: 'data'` (`tms-finance-actions/resource.ts:18`, `userManagement/resource.ts:6`) and the data template is at 717,616 of 1,000,000 bytes (`BUILD_LOG.md:16-22`); a function is function + role + policies + log group + env, the costliest unit H identified. The three homes are the natural ones: `userManagement` already holds the Cognito admin SDK and the owner gate; `tmsFinanceActions` already owns the invoice and payment transactions the triggers live in and reads every table the basis needs (`store.ts:43-62`); `tmsShipmentActions` already owns the shipment counter. (2) **Teams and plans are JSON on `TmsSettings`, not tables.** They are configuration edited by admins, a handful of rows, validated element-by-element on save — exactly `chargeCodes`, `quickPayTiers`, `defaultRequiredReferences` (`:945, :968, :944`) — and a table each would be ≈ 4 KB of template for a list that fits in one item. `UserProfile` is a table because it is per-login and written per invite; `Commission` because it is a ledger; `CommissionPayPeriod` because approval and payment are states on it. (3) **The profile id is the Cognito username.** Every rep field today holds the e-mail (`Order.customerRepId` comments "Cognito username", `:1128`; `getCallerEmail`, `store.ts:130-134`), the Users page derives names from it (`UsersPage.tsx:36`), and a GetItem by the value already on 900 orders is the only lookup that needs no index. (4) **Roles are projected to groups, not read from the table** (above) — the only design that leaves `authorize()` × 5, `hasPageAccess` and the driver app untouched. (5) **Commission rows are immutable once approved; unapproved rows are recomputed in place.** F and G's ledgers (`resource.ts:1447-1449`, `:1558-1559`) never mutate a posted row; a commission before approval is a proposal, after approval a liability, and the ADJUSTMENT/REVERSAL kinds carry every later change with the arithmetic visible. (6) **The trigger is the freeze, not the readiness.** (7) **The fact table is `LaneRateSample`.** (8) **Commission payment is recorded, never executed** — there is no bank path in this stack and SES is denied; a PAID period is bookkeeping with a reference, the `MARK_SENT` idea.
