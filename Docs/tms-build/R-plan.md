# Step R — MVMNT UI, one shipment record, three-business sidebar, Brokerage dashboard (dev)

## Architecture and scope

Planned by Claude Fable (`plan`, planning-only). Sources: `TMS_BUILD_BRIEF.md` "Direction change" (rules 1–4, the hard rules on deletes and Void, the own-fleet rule, subsidiaries, self-serve taxonomy, department views), `Docs/tms-build/MVMNT_UI_REFERENCE.md` §1–5 (shell, list anatomy, dashboard anatomy, detail cards, tokens), `MVMNT_TMS_SPEC.md` §6 (status vocabularies, dashboard charts), `TMS_DESIGN.md` §5–6 (GSI budget, access), `I-plan.md` (`UserProfile`, `RepPicker`, `LaneRateSample` as the fact table, `profitReport`), the Step B backfill mapping (Shipment ↔ Order ↔ Load by `Load.shipmentId`/`Load.orderId`). **Dev data after today's rerun:** Load 941 (892 production + 49 dev fixtures), Shipment 939 (892 `BACKFILL`), LoadCarrier 687 (676 OWN_ASSET / 11 CARRIER), Driver 16, Customer 248, LaneRateSample 847, all 892 backfilled orders `arStatus LEGACY`. Two numbers matter for R: **676 of 687 carrier assignments are own fleet**, so the Ivan Cartage path is the main path, not an edge; and 892 shipments map 1:1 to a Load, so "one record" is a presentation rule over an existing mirror, not a migration. **Rep ids are Cognito usernames (generated `sub`-style ids), not e-mails** — every "by rep" chart joins `UserProfile` for the name, and any legacy e-mail found in a rep field is resolved through `UserProfile.email` by the backfill and logged if unresolved.

R is **presentation + taxonomy + one write path**: (1) a `tms` shell and component kit under `src/features/tms/`, theme scoped to `.tms-shell`, onto which every A–I page is re-skinned under `/tms/*` with redirects from every old path — existing BCAT Ops pages and `NavBar`/`AppLayout` styles untouched; (2) the Shipments page absorbs `/loads` — one list, one detail, the word "Shipment" everywhere, the Order layer hidden (the model stays; every screen resolves the shipment's single order silently and never offers to create a second); (3) revenue taxonomy as data — `OwnershipDivision`, `OwnershipRule`, `ShipmentView` — with `revDivision`/`revSubdivision`/`salesRepId` mirrored on Shipment **and** Load; (4) the own-fleet rule in `tmsShipmentActions`: booking Ivan Cartage writes the mirrored Load's `driverId`, truck, stops and dates, so calendar, dispatch, driver app, settlements and hours/stats see it with zero change to their readers; (5) one sidebar config with four sections read by both shells; (6) `/tms/dashboard`. **No new Lambda; no GSI on Shipment/Load/Order** (slots spent in B–I): division grouping rides on `LaneRateSample` (+`revDivision`, `revSubdivision`, `salesRepId`, refreshed by the existing `--refresh` backfill) and on the `Shipment.status` index. **Deletes:** `scout` greps every router and `apiClient.ts` for `delete`/`DELETE_`/`remove` on Shipment/Order/Load/LoadCarrier; anything found is removed and logged; `VOID_SHIPMENT` (owner/ADMIN from the token, `voidedAt/By/Reason`, PRO kept, AuditLog row, refused on an invoiced shipment) is confirmed present or added. **Judgement calls.** (a) Division codes on the records, division *tree* in a table — a code survives a renamed division and an archived one; rules resolve to a node, the record stores the node's top-level ancestor as `revDivision` and the matched node (if a descendant) as `revSubdivision`, so "any depth" is honoured without a third column. (b) Hand tag beats rules via `revTagSource HAND|RULE`; re-resolve on carrier/driver/customer change only when `RULE`. (c) Seed rows are written by an idempotent Lambda action (`attribute_not_exists(id)`), not a script, so the prod merge seeds itself. (d) Two sidebars, one config: `TmsShell` renders the MVMNT 175px sidebar on `/tms/*`, the existing `NavBar` renders the same `navSections.ts` elsewhere — "existing pages not touched" and "the whole system divided into three sections" both hold. (e) AP lives under Invoicing as a second tab (MVMNT has no AP item; the alternative is a 13th sidebar row). (f) `datPostedAt` is added nullable now so the chart exists; J writes it.

## Schema (`amplify/data/resource.ts`, additive; template ≈ +14 KB, ceiling 20,000 bytes, measured before/after and logged)

**OwnershipDivision** (new; `id` = code): `code!`, `name!`, `brand`, `parentId`, `color`, `sortOrder!`, `active!`, `owners: json` `{building, booking, tracking, invoicing, carrierPay, settlements}` each a party label, `flows: json` `{calendar, dispatch, driverApp, driverPay, fleetDashboards, carShipping}` booleans, `createdBy!/updatedBy!/version!`. **OwnershipRule** (new): `sortOrder!`, `active!`, `name`, `condition: json` `{kind CARRIER_IS|DRIVER_PROGRAM_IS|DRIVER_FLEET_GROUP_IS|CUSTOMER_IS|EQUIPMENT_IS|MODE_IS|LOAD_SOURCE_IS|REFERENCE_MATCHES, value}`, `divisionCode!`, audit fields. **ShipmentView** (new; `id` = slug): `slug!`, `name!`, `department`, `description`, `filters: json`, `columns: string[]`, `sort: json`, `isDefault`, `audience: json` `{groups[], divisions[], roles[]}`, `sortOrder!`, `active!`, audit fields. All three: `allow.authenticated().to(['read'])`, subscriptions disabled, no GSI (tens of rows; `list` is the read), written only by `tmsDirectoryActions`. **Shipment +** / **Load +** (identical names on both): `revDivision`, `revSubdivision`, `revTagSource` HAND·RULE, `revRuleId`, `salesRepId`; **Shipment +** `voidedAt/voidedBy/voidReason` if C did not add them, `datPostedAt`. **LaneRateSample +**: `revDivision`, `revSubdivision`, `salesRepId`. **TmsSettings +**: `ownFleetCarrierId` (the Step C built-in carrier's id, so the rule and the mirror read one source). Nothing renamed, removed or retyped. Seed rows: divisions `BROKERAGE` (BCAT Logistics), `ASSETS` (Ivan Cartage) with children `OWNER_OPERATOR`, `BOX_TRUCK`, `LOCAL`, `CAR_SHIPPING` (Best Care Auto Transport), `COMPANY`; rules in order: carrier is Ivan Cartage → ASSETS; driver program OWNER_OPERATOR → OWNER_OPERATOR; driver fleet group box truck → BOX_TRUCK; driver program LOCAL → LOCAL; mode/equipment vehicle transport → CAR_SHIPPING; catch-all → BROKERAGE. Seed views: Dispatch (ASSETS, pickup today/tomorrow), Tracking (in transit, tracked), POD collection (delivered, POD missing), Accounting (docs needed / unbilled / unpaid), Sales (grouped by rep, quotes → booked), Brokerage board, Car shipping board, Owner operators, Box trucks, Local drivers.

## Pure libs (`src/lib/`, Lambda-shared)

`ownership.ts`: `resolveDivision(divisions, rules, ctx {carrierId, driverProgram, fleetGroup, customerId, equipment, mode, loadSource, references[]})` → `{revDivision, revSubdivision, ruleId}` or the catch-all; `topLevelOf(divisions, code)`; `divisionTree(divisions)`; `validateDivisions` (unique codes, acyclic parents, one top-level per code), `validateRules`; `shipmentContextFor({shipment, load, loadCarrier, driver, customer})` (driver program via `driverProgram.ts`, `Driver.fleetGroup`). `shipmentViews.ts`: `applyView(view, rows)`, `viewsVisibleTo(views, caller)`, `filtersToView(filters)` (save-current-filters), `validateView`. `loadMirror.ts`: `mirrorToLoad(shipment, order, loadCarrier, {driver, truck})` → the exact Load patch `{driverId, truckId, truckNumber, stops, pickupDate, deliveryDate, status?, revDivision, revSubdivision, salesRepId}` and `clearOwnFleetFromLoad()` for an outside carrier — `scout` first lists the precise Load fields `calcDriverPay`, `CalendarPage`, `DispatchPage`, `driver-app-api` and employee hours read, and the patch is built from that list, not from memory. `navSections.ts` (client): the four sections, each `{key, name, brand, items[]}`, items carrying `pageKey`; `visibleSections(caller)`. `dashboardCharts.ts`: the 17 Classic series + Ryne's, every function pure over `{samples, shipments, invoices, bills, checkCalls, documents, profiles}` with a `groupBy DIVISION|SUBDIVISION|REP|CUSTOMER|CARRIER|STATUS|MONTH` and `filters` (division, rep, customer, carrier, mode, status, date window); `p50p90(hours[])`; `podTimingByCarrier` (delivery actual arrival → POD `Document.createdAt`, slowest first); `trackingStats` (share tracked, source, check-call compliance vs `nextCheckCallAt`, hours to first ping — field names confirmed by `scout` from D). `src/types/tms.ts` + the three records; `EntityType` + the three names.

## Lambdas

**`tmsShipmentActions`**: the carrier-booking actions from C (`BOOK_CARRIER`/`ASSIGN_ASSET`/`BOUNCE`/`DISPATCH`, whatever the handler names them) add the mirrored Load to their `TransactWriteItems` — own fleet writes `mirrorToLoad`, an outside carrier writes the clear patch, both CAS on `Load.version`; the same actions, plus `SUBMIT`, customer change and driver change, call `resolveDivision` and write the tag on Shipment and Load unless `revTagSource HAND`; `SET_REV_TAG {shipmentId, divisionCode, subdivisionCode?}` (owner/ADMIN/`page-tms`; `HAND`; `CLEAR_REV_TAG` returns to `RULE` and re-resolves); `SET_SALES_REP {shipmentId, repId}` (a username; mirrored to Load and `Order.customerRepId`); `RETAG_SHIPMENTS {dryRun}` (admin; pages every Shipment, re-resolves `RULE`-tagged rows, writes changed pairs in batches ≤ 90, returns counts by division/subdivision); `VOID_SHIPMENT` as above. **`tmsDirectoryActions`**: `SAVE_DIVISION`, `SAVE_RULES` (whole ordered list), `SAVE_SHIPMENT_VIEW`, `ARCHIVE_*` (sets `active false`, never deletes), `TEST_RULES {shipmentId}` (preview, nothing written), `ENSURE_OWNERSHIP_SEED` (idempotent); all owner/ADMIN. **`laneSamples.ts`** writes the three new fact fields. **`tracking-api`, `driver-app-api`, every own-fleet Lambda, finance, carrier routers: untouched** (the finance router already reads `Load`; no change needed for settlements).
