**Step R invariants J must keep** — each is a test in the plan's test list. (1) **The release gate is the only door into AR.** `src/lib/releaseGate.ts` (`evaluateReleaseGate`, `releaseGateError`, no override anywhere) runs in READY_TO_INVOICE (`tms-shipment-actions/documents.ts:846-871`), SET_AR_STATUS (`handler.ts:4843-4868`), PREVIEW/GENERATE/BATCH invoicing (`tms-finance-actions/invoices.ts:203-205, 370-371, 523`) and PREVIEW_FACTOR/SEND_TO_FACTOR (`factor.ts:77-78, 125`; dispatched `handler.ts:277-280`). A factoring adapter is **never a second door**: the only live `factor` is OTR and it *is* F's `SEND_TO_FACTOR` — the provider page links to it, J does not re-implement it; the HaulPay/Denim/ArtisPay stubs' `factor` is reachable only through `RUN_STUB`, which takes **no shipment** (it runs on the descriptor's sample payload), so there is nothing for a stub to release; and `tmsDirectoryActions` gets no grant on `Shipment`, `Order`, `Invoice` or `FactoringItem` in J, so no J action can set `arStatus`, `invoiceId` or a factoring row even by mistake. (2) **`Load.voidedAt` is read-only to clients and owned by `VOID_SHIPMENT`** (`resource.ts:149-161`; `tms-shipment-actions/handler.ts:5364`). No adapter, router action or OpenAPI route writes it; `tmsDirectoryActions` gets no grant on the Load table; `tracking-api` keeps its existing Shipment/Load **reads** only. Any J path that touches a real shipment runs `assertNotVoided` (`_shared/voided.ts`) first. (3) **No delete path.** `Integration` rows are disconnected (`status DISCONNECTED`) and API clients revoked (`revokedAt`), never deleted; nothing in J writes a Shipment or Load row; `DISCONNECT_INTEGRATION` deletes an SSM parameter and nothing in DynamoDB. (4) **Working set or identity table — every load read says which.** `listLoads()` filters `voidedAt` client-side and `listLoads({ includeVoided: true })` is the identity table (`src/lib/apiClient.ts:207, 292`). The shipment Integrations panel and any provider-page sample read the **working set**; the dashboard's "Posted to DAT" card reads `Shipment.datPostedAt` (`src/lib/brokerageCharts.ts:226-235`) which only a **LIVE** DAT `post` may stamp — a stub never writes it, so the card keeps its `DAT_EMPTY_NOTE` (`:80-81`) until DAT is live; the OpenAPI `GET /api/v1/shipments/<number>` reads the **identity table** and answers a voided shipment with `status VOIDED`, not 404 — a PRO is permanent and a customer system must not learn otherwise. (5) **Vocabulary.** Registry labels, badges, audit `changes.summary`, Academy text and the OpenAPI response say Shipment; the `Order` row is an implementation detail no user or API consumer sees.

**Step R cutover invariants J must also keep** (added with commit `6c6437b`, job 52). (6) **A
Shipment is the only record.** No adapter, provider or import may create a `Load` — the model
grants a signed-in client `read`/`update` only, and `CREATE_SHIPMENT` is the single door. An
integration that ingests freight creates a Shipment, with `customerName` text when it cannot
match a customer record; it never invents a Customer and never writes a bare leg. (7) **A PRO
is claimed, never merely checked.** `ProClaim` rows are keyed by `normalizePro`
(`src/lib/proNumber.ts`) and written with a conditional put inside the shipment transaction;
a claim is never released, so a voided PRO stays dead. Any adapter that brings in an external
PRO passes it as `CREATE_SHIPMENT`'s `pro` and must be prepared for a refusal — it must not
route around the claim with a direct table write. (8) **`aljexId`, `tmsId` and `pickupNumber`
are read-only to clients** alongside `voidedAt`; `SET_LOAD_PRO` is the only way a PRO moves.
(9) **Unresolved customer is refused before the gate, never instead of it** — an adapter that
reaches AR must keep both refusals in that order, and must not treat `DRAFT` as the test for
unresolved, because a backfilled row can be `DELIVERED` and still unresolved.

**Framework.** Three things, each small. (1) **The registry** `src/lib/integrations/registry.ts`: one `ProviderDescriptor` per row above — `key`, `label`, `category` LOAD_BOARD·CAPACITY·TRACKING·COMPLIANCE·FACTORING·ACCOUNTING·FUEL·INSURANCE·RATING·MESSAGING·AI·MAPS·CRM·EDI·API·TELEMATICS, `credentialSource`, `credentialFields [{key, label, secret, hint}]`, `stackSecretNames`, `settingsFields` (the behaviour card, typed), `capabilities` ⊆ `connect·validate·post·track·quote·factor·sync`, `validateHow` (the one read call), `applicability` LIVE_CAPABLE·NOT_APPLICABLE with the reason, `loadsRead` NONE·WORKING_SET·IDENTITY (invariant 4, printed on the page), `docsUrl`. The page, the Lambda and the tests are all driven from it, so adding a provider is one object. (2) **The adapter interface** `Adapter { validate(ctx) → Health; post?(ctx, input) → Result; track?; quote?; factor?; sync? }` with `Result = {mode: 'STUB'|'LIVE', ok, message, externalId?, detail}` and `Health = {status, reason?, detail?, checkedAt}`; `stubAdapter(descriptor)` implements every declared capability; `liveAdapters` exist only for the rows marked LIVE and each is a thin call into the client that already exists (`OtrClient.brokerCheck`, `fetchVehicleLocations`, the BIT `/vehicles/` list, a Google geocode of the office address, Anthropic `models.list`, Slack `auth.test`, Twilio `GET /Accounts/<sid>.json`, QBO `companyinfo`, HubSpot `GET /crm/v3/objects/contacts?limit=1`) — no new provider client is written in J. (3) **The credential store** `_shared/integrationSecrets.ts`: `readPageCredentials(provider)` / `writePageCredentials` / `deletePageCredentials` over `/bcat/integrations/<pool>/<PROVIDER>` (SecureString JSON, `Overwrite: true`, cached 60 s, `ParameterNotFound` → null, any other error thrown — the `readConnectionConfig` rules, `pod-actions/handler.ts:385-406`); `readStackSecret(name)` returns `{value, neutered: value === 'disabled-on-dev'}`; `maskOf(fields)` keeps last 4 of each secret field and nothing else; `redactSecrets(text, values)` runs over every message before it reaches `healthDetail`, an `AuditLog` row or a log line. **Secrets never land in DynamoDB or the template**: `Integration.credentialRef` is the parameter name or the secret names, `credentialMask` is last-4s.

**Stub mode is honest by construction.** A stub result's `mode` is `'STUB'`, its `message` begins `STUB —`, its `externalId` is `stub:<uuid>` (never a plausible provider id). A stub **never touches a business record**: no `Load.trackingProvider`, no `Shipment.datPostedAt`, no `FactoringItem`, no `Invoice` field; it writes exactly one `AuditLog` row — `entityType 'INTEGRATION'` (the column is a free `a.string()`, `resource.ts:2737`, so no schema change; the client `EntityType` union at `src/types/index.ts:412` gains `'Integration'`), `action 'STUB_<CAP>'`, `changes {stub: true, provider, summary}` — and bumps `Integration.lastStubAt`/`stubCount`. In the UI a STUB result renders under an orange **Stub** `TmsBadge` with the sentence "No call was made to <Provider>"; a provider page whose `mode` is STUB says **Stub mode** in its header; the shipment's Integrations panel never enables a live button for a provider that is not CONNECTED and never offers a stub on a voided shipment. `validate` on a STUB provider never answers CONNECTED: it answers `UNABLE_TO_VERIFY · NO_CREDENTIALS` (or `NOT_APPLICABLE` with the reason). A STACK secret whose value is the literal `disabled-on-dev` answers `UNABLE_TO_VERIFY · NEUTERED_ON_DEV`, badge "Live on main · neutered on dev" — never INVALID_CREDENTIALS, never CONNECTED. **A provider whose credentials are absent** is a row with `status NOT_CONNECTED`, `mode STUB`, an empty credentials card listing exactly the fields it needs (from the descriptor — the same list the build log carries), a behaviour card that is still editable (DAT's contact method can be set before the key arrives), and *Run stub* buttons under *What this feeds*. **How `validate` reports health**: `VALIDATE_INTEGRATION` runs the descriptor's one read call with a 10 s budget, maps the outcome to `health` OK·INVALID_CREDENTIALS·UNABLE_TO_VERIFY with `healthReason` NO_CREDENTIALS·NEUTERED_ON_DEV·PROVIDER_UNREACHABLE·NO_VALIDATE_ENDPOINT·NOT_APPLICABLE·STUB and a redacted `healthDetail`, stamps `lastCheckAt/By` and `lastOkAt`, appends to `events` (≤ 50, the Quote precedent, `tms-shipment-actions/quotes.ts:183, 213-214`) and writes `AuditLog INTEGRATION <provider> VALIDATE`; a 401/403 is INVALID_CREDENTIALS, anything else that is not a 2xx is UNABLE_TO_VERIFY with the status code; **Checking connection** is the page's pending state, not a stored one. The state badge is `status` × `health`: NOT_CONNECTED (gray), CONNECTED (green; status CONNECTED, health OK), INVALID_CREDENTIALS (red), UNABLE_TO_VERIFY (orange), DISCONNECTED (gray) — the kit's `TmsTone`s, no new colour. BRIDGE providers compute health **read-side**: the page reads the newest row the bridge writes (`IntakeItem.externalSource 'gmail'`, `FactoringItem`, `VendorPayable source EMAIL`, `FuelTransaction`, `AmazonDispute` — all `allow.authenticated()` reads) and shows "last message received <when>" — no Lambda grant, no polling table.

**Judgement calls.** (1) **No new Lambda; `tmsDirectoryActions` carries J.** Every router is `resourceGroupName: 'data'` and the data template is **749,425 bytes after the Step R cutover, 250,575 under the 1,000,000-byte cap** (`BUILD_LOG.md`, the cutover entry; re-measure with `node scripts/measureDataTemplate.mjs` before J's first schema change); a function is function + role + policies + log group + env, the costliest unit H identified. `tmsDirectoryActions` already owns `TmsSettings` and the org's configuration writes, already carries a `secret()` (`GEOCODE_TOKEN_SECRET`, `tms-directory-actions/resource.ts:16`), already has the owner/ADMIN `authorize` (`handler.ts:158`), and a validate is one HTTPS call inside its 30 s.
