**Framework.** Three things, each small. (1) **The registry** `src/lib/integrations/registry.ts`: one `ProviderDescriptor` per row above — `key`, `label`, `category` LOAD_BOARD·CAPACITY·TRACKING·COMPLIANCE·FACTORING·ACCOUNTING·FUEL·INSURANCE·RATING·MESSAGING·AI·MAPS·CRM·EDI·API·TELEMATICS, `credentialSource`, `credentialFields [{key, label, secret, hint}]`, `stackSecretNames`, `settingsFields` (the behaviour card, typed), `capabilities` ⊆ `connect·validate·post·track·quote·factor·sync`, `validateHow` (the one read call), `applicability` LIVE_CAPABLE·NOT_APPLICABLE with the reason, `docsUrl`. The page, the Lambda and the tests are all driven from it, so adding a provider is one object. (2) **The adapter interface** `Adapter { validate(ctx) → Health; post?(ctx, input) → Result; track?; quote?; factor?; sync? }` with `Result = {mode: 'STUB'|'LIVE', ok, message, externalId?, detail}` and `Health = {status, reason?, detail?, checkedAt}`; `stubAdapter(descriptor)` implements every declared capability; `liveAdapters` exist only for the rows marked LIVE and each is a thin call into the client that already exists (`OtrClient.brokerCheck`, `fetchVehicleLocations`, the BIT `/vehicles/` list, a Google geocode of the office address, Anthropic `models.list`, Slack `auth.test`, Twilio `GET /Accounts/<sid>.json`, QBO `companyinfo`, HubSpot `GET /crm/v3/objects/contacts?limit=1`) — no new provider client is written in J. (3) **The credential store** `_shared/integrationSecrets.ts`: `readPageCredentials(provider)` / `writePageCredentials` / `deletePageCredentials` over `/bcat/integrations/<pool>/<PROVIDER>` (SecureString JSON, `Overwrite: true`, cached 60 s, `ParameterNotFound` → null, any other error thrown — the `readConnectionConfig` rules, `pod-actions/handler.ts:385-407`); `readStackSecret(name)` returns `{value, neutered: value === 'disabled-on-dev'}`; `maskOf(fields)` keeps last 4 of each secret field and nothing else; `redactSecrets(text, values)` runs over every message before it reaches `healthDetail`, an `AuditLog` row or a log line. **Secrets never land in DynamoDB or the template**: `Integration.credentialRef` is the parameter name or the secret names, `credentialMask` is last-4s.

**Stub mode is honest by construction.** A stub result's `mode` is `'STUB'`, its `message` begins `STUB —`, its `externalId` is `stub:<uuid>` (never a plausible provider id). A stub **never touches a business record**: no `Load.trackingProvider`, no `FactoringItem`, no `Invoice` field; it writes exactly one `AuditLog` row `entityType 'INTEGRATION'`, `action 'STUB_<CAP>'`, `changes {stub: true, provider, summary}` (`resource.ts:2579-2592`) and bumps `Integration.lastStubAt`/`stubCount`. In the UI a STUB result renders under an amber **Stub** chip with the sentence "No call was made to <Provider>"; a provider page whose `mode` is STUB says **Stub mode** in its header; the shipment's Integrations panel never enables a live button for a provider that is not CONNECTED. `validate` on a STUB provider never answers CONNECTED: it answers `UNABLE_TO_VERIFY · NO_CREDENTIALS` (or `NOT_APPLICABLE` with the reason). A STACK secret whose value is the literal `disabled-on-dev` answers `UNABLE_TO_VERIFY · NEUTERED_ON_DEV`, badge "Live on main · neutered on dev" — never INVALID_CREDENTIALS, never CONNECTED. **A provider whose credentials are absent** is a row with `status NOT_CONNECTED`, `mode STUB`, an empty credentials card listing exactly the fields it needs (from the descriptor — the same list the build log carries), a behaviour card that is still editable (DAT's contact method can be set before the key arrives), and `Run stub` buttons under *What this feeds*. **How `validate` reports health**: `VALIDATE_INTEGRATION` runs the descriptor's one read call with a 10 s budget, maps the outcome to `health` OK·INVALID_CREDENTIALS·UNABLE_TO_VERIFY with `healthReason` NO_CREDENTIALS·NEUTERED_ON_DEV·PROVIDER_UNREACHABLE·NO_VALIDATE_ENDPOINT·NOT_APPLICABLE·STUB and a redacted `healthDetail`, stamps `lastCheckAt/By` and `lastOkAt`, appends to `events` (≤ 50, the Quote precedent) and writes `AuditLog INTEGRATION <provider> VALIDATE`; a 401/403 is INVALID_CREDENTIALS, anything else that is not a 2xx is UNABLE_TO_VERIFY with the status code; **Checking connection** is the page's pending state, not a stored one. The state badge is `status` × `health`: NOT_CONNECTED, CONNECTED (status CONNECTED, health OK), INVALID_CREDENTIALS, UNABLE_TO_VERIFY, DISCONNECTED. BRIDGE providers compute health **read-side**: the page reads the newest row the bridge writes (`IntakeItem.externalSource 'gmail'`, `FactoringItem`, `VendorPayable source EMAIL`, `FuelTransaction`, `AmazonDispute` — all `allow.authenticated()` reads) and shows "last message received <when>" — no Lambda grant, no polling table.

**Judgement calls.** (1) **No new Lambda; `tmsDirectoryActions` carries J.** Every router is `resourceGroupName: 'data'` and the data template stood at **718,390 bytes before I and ≈ 732,237 after** (the lead's measurement after job 39; re-measure with `node scripts/measureDataTemplate.mjs` before J's first schema change); a function is function + role + policies + log group + env, the costliest unit H identified. `tmsDirectoryActions` already owns `TmsSettings` and the org's configuration writes, already carries a `secret()` (`GEOCODE_TOKEN_SECRET`, `resource.ts:16`), already has the owner/ADMIN `authorize` (`handler.ts:135`), and a validate is one HTTPS call inside its 30 s. What it gains: eight `secret()` env entries (the STACK providers it must validate — the dev Aspect neuters the same three on it automatically, which is exactly what makes the dev badge truthful), `INTEGRATION_TABLE_NAME` + Get/Put/Update/Scan, `INTEGRATION_PARAM_PATH` + `ssm:GetParameter/PutParameter/DeleteParameter` on `/bcat/integrations/<pool>/*`, `ssm:GetParametersByPath` on `/bcat/dispatch/<pool>/*` (Twilio status, read-only). Rejected: a `tms-integration-actions` function (≈ 8–12 KB for one more router) and validating by `lambda:Invoke` of each owning Lambda (less bytes, more coupling — kept as drop-order item 2). (2) **One `Integration` model, no GSI, and API clients are rows in it.** ≤ 40 provider rows and a handful of API clients; `list` is the read; an API client is `id api:<clientId>`, `kind API_CLIENT`, its secret's hash in the OPENAPI parameter, never in the row. Rejected: `IntegrationEvent`/`EdiTransaction` models now — events live on the row (≤ 50) and in `AuditLog`; the EDI log is bytes for traffic that cannot arrive before a trading partner exists. (3) **Page credentials go to SSM under the pool id, the JobsDone way.** The brief's "no SSM" is a production rule; `/bcat/integrations/<devPoolId>/…` is a dev path the dev stack creates, exactly as `/bcat/pods/<pool>/connection` already is, and the IAM resource ARN is scoped to it. Secrets Manager is not introduced: nothing in the stack uses it and a second store is a second rotation story. (4) **Stack secrets are shown, validated, never edited.** Writing `/amplify/*` from a Lambda is both forbidden and wrong (Amplify owns those paths); the page prints the secret *names* and the console command. (5) **Live per-shipment actions are the ones that exist.** The shipment's Integrations panel offers Send to Factor (F's `SEND_TO_FACTOR`), the tracking link (D), the geocode (implicit) — J adds **no new live action on a shipment**; a Post-to-DAT that pretends is the fake success this step must not ship. (6) **QuickBooks: connect and preview, do not push.** OAuth connect, `companyinfo` validate, account/charge-code mapping cards and a pure payload preview ship; pushing invoices needs the mappings confirmed and K's Errors tab with Retry to be honest about failures (spec `:380`), so `sync` is STUB in J with the payload visible. (7) **`Load.trackingProvider` is not extended** — a value nothing can start is a lie in a picker (`TMS_DESIGN.md:343`). (8) **No provider client is written for a provider nobody can call.** Stubs are the whole of DAT, Truckstop, Parade, etc. in J; their live adapters are a credential away and each is its own small pass with a test against the real sandbox.

## Schema (`amplify/data/resource.ts`)

**Integration** (new; `id` = provider key, or `api:<clientId>`; Put with `attribute_not_exists(id)`): `provider!`, `kind!` PROVIDER·API_CLIENT, `category`, `mode!` STUB·LIVE, `credentialSource!` NONE·STACK·PAGE·BRIDGE·SCRIPT·OWN, `credentialRef` (parameter name, or the comma-joined secret names — pointers only), `credentialMask: json` ([{key, last4}]), `status!` NOT_CONNECTED·CONNECTED·DISCONNECTED, `health!` UNKNOWN·OK·INVALID_CREDENTIALS·UNABLE_TO_VERIFY, `healthReason`, `healthDetail`, `lastCheckAt`, `lastCheckBy`, `lastOkAt`, `settings: json` (the behaviour card, validated against the descriptor), `capabilities: string[]`, `lastStubAt`, `stubCount`, `connectedAt`, `connectedBy`, `disconnectedAt`, `disconnectedBy`, `name` / `scopes: string[]` / `lastUsedAt` / `expiresAt` / `revokedAt` (API clients), `events: json` (≤ 50), `createdBy!`, `updatedBy!`, `version!`. **No GSI.** `allow.authenticated().to(['read'])`, subscriptions disabled, written only by `tmsDirectoryActions` (and `tracking-api` for `lastUsedAt`). **TmsSettings +** (all optional): `trackByDefault` (true), `autoStatusFromGeofence` (false), `trackingIntervalMin` (30), `trackingDurationHours` (72) — row J's shared tracking toggles; `postalCodeAliases: json` `[{zip, city, state}]`; `hubspotPortalId`; `integrationsNotifyChannel` (Slack channel for health changes — stored, used by K). **Customer +**: `project44CustomerId`, `hubspotId`, `ediSettings: json` `{isaId, gsId, autoAccept, skip210, skip997}`, `haulpayDebtorId` (stored for a future factor; null). **UserProfile +**: `hubspotId`, `truckstopAuthorizedAt` (per-user OAuth placeholder, null until live). `Carrier`, `Load`, `LoadCarrier`, `Order`, `Shipment`, `Invoice`, `Quote`: unchanged — `Load.trackingProvider` keeps its five values. Storage: nothing. **Template budget.** 732,237 bytes today (lead's figure). J: one model ≈ 3.5 KB; ≈ 14 additive fields ≈ 1 KB; on `tmsDirectoryActions` eight `secret()` env entries, two SSM statements and one table ARN/env ≈ 2 KB; on `tracking-api` one SSM statement, one table grant ≈ 0.7 KB — **≈ 7–8 KB, planned ceiling 12,000 bytes → ≈ 744 KB after J, ≥ 256 KB for K's `WorkflowRun` (+ 2–3 GSIs ≈ 5 KB) and M's assistant Lambda (≈ 8–12 KB by H's accounting)**. Measured before the first schema change and after the last, both numbers in the J `BUILD_LOG` entry. **Drop order if the post-J size passes 745,000 bytes:** (1) the two OpenAPI routes and their grants on `tracking-api` (the page still issues clients; the endpoints wait); (2) the eight stack-secret envs on the router — STACK providers then validate by `lambda:InvokeFunction` of their owning Lambda's existing read action; (3) `Integration` folded into `TmsSettings.integrations: json` with the same fields (last resort — API clients then lose their own version/events).
