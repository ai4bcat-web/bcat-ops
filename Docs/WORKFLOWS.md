# BCAT Ops Workflows

## How pages consume data
- Pages load data via custom hooks in `src/hooks/*`.
- Hooks call `src/lib/apiClient.ts`, which talks to the AppSync endpoint in `amplify_outputs.json`.
- Auth state flows from `AuthProvider` -> hooks -> pages.

## Page access
- The owner (`ryne@bcatcorp.com`) and members of the Cognito `ADMIN` group (the Users page "Make admin" toggle) bypass page permissions and see every page. Every other account needs an explicit `page-<key>` Cognito group for each page; no grants means no page access. The legacy admin email allowlist grants feature privileges only, not pages.
- The sidebar, global shortcuts, cross-page links, and direct-route guards use the same `hasPageAccess` check. Denied URLs redirect to an allowed landing page, or show No page access when none is granted.
- Users page toggles save the explicit allowlist. Permission edits are disabled while a save is pending. Sessions refresh Cognito grants at startup, when the tab regains focus/visibility, and every minute while visible.
- These checks govern web pages and navigation; they are not a substitute for AppSync or S3 resource authorization.

## UI interaction conventions
- Forms use `react-hook-form` + `@hookform/resolvers` + Zod.
- Toasts use `sonner`.
- Tables use `@tanstack/react-table`.
- Calendar uses FullCalendar v6 with `resource-timeline` plugin.
- Modals use shadcn dialog/popover primitives.

## State decisions
- Local UI state: React state inside the page/component.
- Shared view state: Zustand in `src/store/useAppStore.ts`.
- Server-backed data: fetched from hooks when a page loads.
- Do not lift transient UI state into global stores unless reused by multiple pages.

## Failure behavior
- Auth errors redirect to `/login`.
- Data loading errors show a toast and render an empty state.
- Calendar errors preserve the last loaded date range.

## Acceptable change styles
- Add a feature in-place if it fits an existing folder.
- Add new files/folders only when the new domain is clearly separate.

## Repair invoice intake
- `scripts/ingestMaintenanceInvoice.mjs` writes emailed invoices as `PENDING`; staff post or archive them in the invoice Review Queue. Fleet spending excludes pending and archived records.
- Intake and the app invoice list follow every AppSync `nextToken` page. Intake fails closed on incomplete list/create responses.
- Numbered invoices retain the document-content `externalId` (date, normalized vendor, amount, normalized invoice number). Unnumbered invoices can supply `sourceDocumentId` to distinguish separate documents with equal totals. Source identity must be stable across retries.
- New emailed records use deterministic IDs. AppSync create conflicts count as duplicates only after retrieving the existing record and verifying its immutable `externalId`. Reviewed and archived rows remain in duplicate checks.
- `node scripts/dedupeMaintenanceInvoices.mjs` is a read-only preview; `--apply` archives only unambiguous extras. No records are deleted. Groups spanning different assigned units require manual review, since a legacy invoice may be split across trucks. Unnumbered records are not grouped by content alone.
- Do not use an invoice date cutoff to hide missing historical invoices, or email Seen status as proof of successful ingestion. Do not claim complete repairs-address coverage from the forwarded Gmail copy alone.
- A new invoice can be split across several units; each line carries its own equipment, amount and "what was fixed on this unit", and becomes its own invoice record with that description. Lines left blank fall back to the invoice-level description. Editing an existing invoice stays single-unit.

## Factoring queue
- Operations → **Factoring Queue** (`/factoring`, page grant `factoring`) tracks one row per PRO from the subject `Invoice for PRO #12345`; forwards, mixed case, whitespace, a missing `#`, trailing punctuation and alphanumeric PROs (`945143JJ`) are accepted. Leading zeroes are preserved and letters are upper-cased.
- New rows start **Need to factor**. Staff change the row to **Pending with OTR** or **Factored** using its status selector. These are tracking statuses; changing them does not send an invoice to OTR.
- `scripts/factoringEmailBridge.gs` runs in the existing BCAT Intake Bridge Apps Script project, on the `ai4bcat@gmail.com` mailbox, every five minutes once installed. The `ivanfactoring@bcatcorp.com` distribution list must deliver each message to that mailbox. Setup is in `SETUP.md`, Section 10.
- The bridge checks recipient headers, including the Google Group List-ID, regardless of read/archive status. Per-message acknowledgements allow new messages in old threads; a rotating backlog scan covers older mail. Missing/invalid PRO subjects get the Gmail `factoring-needs-review` label instead of a guessed identifier. Forward again with the corrected subject to ingest them.
- The secret-authenticated `factoring-intake` Lambda creates `FactoringItem` with `id = proNumber` using an atomic conditional put. Re-forwarding the same PRO is a no-op, including after staff mark it Factored; it never creates a duplicate or resets the status. The page follows all AppSync pages and polls every 30 seconds.
- Grant staff **Factoring Queue** on the Users page; other page permissions remain unchanged. Only members of the Cognito **ADMIN** group see the row's trash button; the `FactoringItem` model refuses `delete` from anyone else, so the restriction holds even outside the UI. Deleting removes the queue row only — the email stays in the mailbox, and forwarding it again recreates the row.

## Vendor AP queue
- Operations → **Vendor AP Queue** (`/vendor-ap`, page grant `vendorAp`) tracks vendor invoices that need to be paid. Two statuses: **Need to pay** and **Done**. Rows come from two sources: an unpaid maintenance invoice sent from the Invoices page (send icon; only rows with no payment date offer it), or an email forwarded to `vendorpayments@bcatcorp.com` via `scripts/vendorApEmailBridge.gs` → `vendor-ap-intake` (original message text and attachments are kept; nothing is parsed or guessed).
- Every write goes through the `manageVendorPayable` Lambda (`SEND_MAINTENANCE`, `UPDATE_DETAILS`, `COMPLETE`, `REOPEN`); the `VendorPayable` model itself is read-only for staff and delete-only for the Cognito ADMIN group. Send from a maintenance invoice is deterministic (`maintenance:<invoiceId>`): re-sending refreshes the read-only snapshot and reports "already in Vendor AP", never a second row, and never resets a Done row. Each maintenance row is its own payable; split invoices are sent per equipment line.
- **Mark done** requires a payment method and date (optional reference / check #). For a maintenance-linked row the payment is written to the AP row and the source `MaintenanceInvoice.paymentMethod/paymentDate` in one DynamoDB transaction guarded by both rows' `updatedAt`, so the Invoices page stops counting it as unpaid; if the source was paid or edited by someone else first, the action fails with a refresh prompt and nothing changes. **Edit payment** corrects a Done row the same way; **Reopen** clears both sides. Email rows have editable vendor / invoice # / amount / date / description; maintenance rows show the source snapshot read-only.
- Only ADMIN sees the trash button; deleting removes the queue row only (the source invoice, email, and files stay).

## Motive fault codes
- `GET https://api.gomotive.com/v1/fault_codes?status=open` (header `X-Api-Key`) is the source; the `motive-fault-sync` Lambda pages it hourly, matches `vehicle.number` to Equipment the same way the mileage/location syncs do (`motiveVehicleNumber` overrides `unitNumber`, unmatched vehicles key as `motive:<number>`), and writes one `TruckFaultCode` row per (truckId, faultId). Retired trucks stay in that match map — an active claim on the same number wins — so a retired truck's codes keep pointing at its Equipment row instead of reappearing as an unknown vehicle.
- The table IS the live fault list: every run deletes rows Motive no longer reports as open, including when it reports none, so a repaired truck clears itself. Nothing here is entered by hand.
- The Fleet Manager Dashboard shows them in **Active Fault Codes · Motive**, directly under the miles-until-next-PM tracker. Trucks marked inactive in Fleet are hidden from the cards and the counts; a Motive vehicle with NO Equipment record still shows under its Motive number, flagged "no matching truck in Fleet", so a real open fault is never dropped silently. Each card includes the code, meaning (`fmi_description`), controller, last observation, and time open.

## Amazon mileage expenses
- In Amazon Driver Pay settings, add an expense or select an existing revision and choose Change, then Mileage calculation. Enter cost per mile, miles for the weekly expense, and an effective date. Apply the draft, then Save settings.
- Amount is calculated from cost per mile × entered miles and rounded once to cents; sub-cent per-mile rates are retained. These are entered miles, not an ELD feed or automatic trip-mile total.
- Both inputs are saved on each expense revision in the existing fixedExpenses JSON. Reopening a revision restores its calculation; changes retain previous amounts and formulas. Partial periods still prorate by calendar day.
- Mileage controls are enabled for Amazon settings only; box-truck fixed-amount entry is unchanged.
- A fixed expense is shared through the pay split by default (an after-expenses driver bears only their pay % of it); "Driver pays in full, after the split" is available per line for charges the driver owes outright. An optional company share on any line stays off the statement and is booked as a company cost in Finances (e.g. the company's half of a truck lease). Weekly lease mileage: on the settlement week, Add expense → **Miles × cost per mile** — the amount is computed, the basis is written into the description, and it is deducted before the split for that week only.
- Weekly mileage is entered per settlement week on the driver's card: the Deductions block carries blank Miles and $/mi inputs, shows the computed total, and Add writes a one-off `Lease mileage — N mi @ $R/mi` deduction for that week only (`mileageDeductionLine` in `src/lib/mileageDeduction.ts`, shared with the Add expense sheet). Inputs are blank on every week and driver; a saved row is removed with its trash button. Use this, not a fixed-expense revision, when the miles change week to week.
- Each driver's settlement card shows **Shipments** — the number of trip rows on that driver's week, the same rows in the trips table (a posted DISPUTE recovery counts as one). The CSV and PDF statements carry the same figure as a "Total shipments" line; credits, debits, deductions, and fuel are never counted.

## Amazon disputes (driver portal)
- Drivers file disputes at `/amazon-disputes` (public, no login). Evidence is one field — the trip confirmation email first (any image type, or a PDF), then up to five more files as proof, 10 MB each. The first file is sent as the `CONFIRMATION` and the rest as `PHOTO`; files go to `dispute-proofs/{submissionId}/` via a presigned PUT, then the `dispute-portal-api` Lambda verifies each object and writes one `AmazonDispute` row (`source DRIVER_PORTAL`, `status PENDING`). Retrying a submission reuses its id, so a retry never creates a second row.
- Staff work the queue at `/disputes`. Rows carry a **Pay period** column and are always ordered by it — newest week first, filing time breaking ties; legacy free-text periods from the old Google Form (no year) sit below every dated week, and the status tabs and search never change that order. The Proof cell opens a Files sheet: every upload has a thumbnail, Open, Download, and Download all — downloads fetch the presigned object and save a blob, so a screenshot never replaces the page you were working (see `src/lib/download.ts`).
- A manual dispute on `/disputes` works exactly like the portal: the driver comes from the active roster dropdown, the 7-day period is a Sunday-week dropdown (prefilled from the shipment date, legacy hand-typed values stay selectable), and evidence is ONE field — first file badged and filed as the trip confirmation, the rest as proof, six files per dispute counting the staff files already stored. Staff uploads live under `dispute-staff-proofs/{disputeId}/` — their own prefix, so staff can replace or remove them while the driver's `dispute-proofs/` files stay untouchable. Remove a stored staff proof to free a slot (or to replace the confirmation); every save carries portal and Amazon-response files through untouched, and a failed save cleans up the objects it just uploaded.
- Changing the status chip on a row opens the update sheet with that status preselected; the speech-bubble button next to it opens the same sheet without changing status (blue once a response is on file). One save writes status, `amazonResponse`, `amazonResponseAt`/`By`, `resolvedAmount` (when Paid) and the evidence array. The Amazon screenshot is pasted (⌘V), dropped or browsed — image or PDF, 10 MB max — and uploads to `dispute-responses/{disputeId}/` before the row is written. The list polls every ~30 s because portal writes bypass AppSync subscriptions.
- Setting a dispute to Paid offers "Add to settlement week": a Sunday week (next week back through ten) plus the driver's pay account, prefilled by matching the typed portal name against the active roster. Saving writes an `AmazonTrip` on that week — `loadId` `DISPUTE <shipment date>`, freight = recovered amount, status Completed, the trip number in `notes` — so the recovery appears as an ordinary shipment labelled DISPUTE and pays at the driver's normal percentage. `settlementTripId`/`settlementPeriodStart`/`settlementDriverId` are stored on the dispute row.
- That trip id is what keeps a recovery from being paid twice: re-saving moves or re-prices the same row, choosing "Don't add" or leaving Paid deletes it. A row someone deleted on the settlement page is written fresh; any other write failure surfaces instead of creating a second row. A recovery with no amount keyed is refused. The dispute row shows the settlement week it was paid out on.
- Deleting a dispute deletes its settlement shipment first, and the edit sheet keeps an existing posting honest: a status that is no longer Paid drops the row, a re-keyed recovered amount re-prices it on the week it was posted to. Nothing can leave a `DISPUTE` row on a check with no dispute behind it.
- The driver's `dispute-proofs/` files are carried through every staff save untouched (`mergeDisputeEvidence` in `src/features/disputes/disputeEvidence.ts`) — staff have no write or delete grant on that prefix, and the row is the only index of those objects. Staff response screenshots live in their own prefix and can be removed; the S3 object is deleted only after the row stops referencing it.
- Deleting a dispute on `/disputes` removes the row only; its `dispute-proofs/{id}/` uploads are kept on purpose (a deleted row can be re-filed, and staff have no delete grant on that prefix). Clean up by hand with `aws s3 rm`, or add a bucket lifecycle rule if volume ever warrants it.
- The endpoint is published as `custom.disputePortalUrl` in `amplify_outputs.json`; `VITE_DISPUTE_PORTAL_API_URL` overrides it locally.

## Quotes
- Customer quotes and carrier offers live on `/quotes` (Sales → Quotes, page grant `quotes`), one quote on `/quotes/:id`, the lane history on `/rates`, and the buy side on a shipment's Carrier tab. Every write is a `tmsShipmentActions` action; the public answer page is `/quote/:token` on the `tracking-api` Function URL. Sell-side actions need owner/ADMIN/`page-quotes`; offer actions accept `page-loads` or `page-quotes`; `ACCEPT_OFFER` needs exactly what `BOOK_CARRIER` needs; `SAVE_QUOTE_SETTINGS` is owner/ADMIN.
- Sell side, end to end:
  1. **New quote** on `/quotes`, or from a customer's Quotes tab in the directory → pick the customer, the stops, the equipment and the charge lines → **Save**. It lands `DRAFT`; a request somebody phoned in lands `REQUESTED` and shows on the **To price** tab.
  2. Read the pricing warnings on the form. Below the margin floor and below the customer's minimum profit must each be acknowledged by key, and while `quoteBelowMinMarginAdminOnly` holds only an admin may send them; over max profit and over top spend are stated and never block.
  3. **Send…** → `SEND_QUOTE` writes `QUOTED`, mints the round's `linkToken`, sets `expiresAt` (customer hours → org `hoursToQuote` → 24 h) and moves the customer's lead stage to QUOTED. On dev SES is denied: the dialog returns NOT_SENT with the link and the body to send by hand.
  4. The customer answers on `/quote/<token>` — Accept (`RECEIVED_REPLY`), Counter (`RECEIVED_COUNTER`) or Decline with a reason (`LOST`). The token is REMOVEd by the answer, so each round's link works once; an expired link closes the quote LOST/EXPIRED when it is opened.
  5. On a counter, either **Accept counter** (`ACCEPT_COUNTER` absorbs the difference into the line haul only and lands `RECEIVED_REPLY`) or **Counter…** (`COUNTER_QUOTE`: new number, new token, `rounds` + 1, `SENT_COUNTER`).
  6. **Convert to shipment** (`CONVERT_QUOTE`, offered on `QUOTED` / `SENT_COUNTER` / `RECEIVED_REPLY`, never expired) → credit check, then the ordinary `CREATE_SHIPMENT` → `SAVE_ORDER_FORM` → `SUBMIT_ORDER` path, then one transaction stamps the quote `WON`, writes `Order.quoteId`/`quoteNumber`/`quoteAmountCents`/`quoteNotes` and closes the group's siblings (priced → LOST, unpriced → CANCELED). A shipment that prices to anything other than the quoted number is refused and soft-deleted.
  7. Otherwise close it: **Mark lost** (`MARK_QUOTE_LOST`), **Cancel** (`CANCEL_QUOTE`) or **Pass** (`PASS_QUOTE`, sell side only). `RESTORE_QUOTE` puts a LOST/CANCELED quote back on `QUOTED` with no token — a link is only ever minted by a send. `REVERT_TO_QUOTE` is the one way back out of WON (no UI button; refused once a second order, an active/TONU carrier or an invoice exists).
- Buy side, on the shipment's Carrier tab:
  1. **Request offers** (`REQUEST_OFFERS`) → pick up to 25 bookable carriers → one `REQUESTED` row per carrier under one `groupId`, each with its own token and an `expiresAt` capped at the first pickup appointment (minimum 1 h), addressed to each carrier's DISPATCH contacts.
  2. A price given on the phone is **Log offer** (`LOG_OFFER`) → `QUOTED`, no token, no clock.
  3. The carrier answers on `/quote/<token>` — Quote a price, Accept, Counter or Pass. An accept writes `RECEIVED_REPLY` and books nothing; the book-now rate is only offered while `quoteOffersCarrierSeesBookNow` holds.
  4. **Counter offer** (`COUNTER_OFFER`) sends our number back with a fresh token; **Reject** (`REJECT_OFFER`) closes one offer LOST.
  5. **Accept** (`ACCEPT_OFFER`) runs `BOOK_CARRIER` with the offer's rate: the gate, the assignment, `LoadCarrier.quoteId`, the offer's `WON` stamp and the sibling closes are one transaction. Covering the load any other way (book, assign, own-asset dispatch) cancels its remaining open offers.
- Lane history: `LaneRateSample` (`lrs:<loadId>`, overwritten, never doubled) is written from `tmsShipmentActions` for every delivered load that has a `LoadFinancials` row and a lane key, and re-written whenever cost or revenue can still move; a load canceled or TONU'd afterwards is marked `excluded` and kept. The panel keys on `CITY|ST>CITY|ST`, falls back to the ZIP3 pair and then to "No history on this lane", and leaves OWN_ASSET legs out of the carrier side unless the box is ticked. `scripts/backfillLaneSamples.mjs` loaded the pre-existing loads.
- Expiry is lazy: `SWEEP_EXPIRED_QUOTES` runs once per `/quotes` mount (conditioned per row, so a quote answered a second earlier is skipped) and a lapsed link expires itself on the next read.

## Users & roles
- People live on `/users` (off the sidebar; the **Roles & pages** card in Settings links to it). The route is `RequireAdmin` — owner or the Cognito `ADMIN` group — and every write is a `manageUsers` action on the `userManagement` Lambda, which re-checks the caller itself: *"Forbidden: managing users requires owner or ADMIN."* Three things stay the owner's and are refused for anybody else: `setAdmin` (*"Forbidden: only the owner may grant or revoke admin."*), `delete` (*"Forbidden: only the owner may delete a user."*) and `setRole` or `create` with the ADMIN role (*"Forbidden: only the owner may grant the ADMIN role."*).
- **A role is data on `UserProfile`, projected onto Cognito groups** (`src/lib/roles.ts`): the `ADMIN` group for an admin, `role-<ROLE>`, a `page-<key>` for every page in `ROLE_PAGES[role]` and every `extraPages` grant, and `claim-<CLAIM>` per claim. Nothing reads the table to authorize — every gate still reads `cognito:groups` off the token — so **a role change takes effect at the user's next sign-in**; `forceSignOut` (Force sign-out on the card) drops every session and makes it land now. `reconcileGroups` removes only the groups this projection owns, so `DISPATCHER` and any group another feature granted survive.
- `ROLE_PAGES`: ADMIN → the `ADMIN` group (every page, so the matrix row is ticked throughout); MANAGER → `loads · customers · carriers · locations · quotes · invoicing · carrierPay · reports · commissions · audit`; CUSTOMER_REP → `loads · customers · locations · quotes · invoicing · reports · commissions`; CARRIER_REP → `loads · carriers · locations · quotes · carrierPay · reports · commissions`; AR_AP → `invoicing · carrierPay · vendorAp · factoring · reports`; COMPLIANCE → `carriers · customers · locations`; NONE → nothing. The Settings matrix is read-only on purpose — a role's pages are code, re-applied on every profile save. Pages beyond the role are per-user `extraPages`; `setPageGroups` touches only `page-*` groups and cannot revoke one the role grants.
- **Claims** (`CLAIMS`) are recorded on the profile and mirrored to `claim-*` groups; only `ENFORCED_CLAIMS` — `CREDIT_LIMIT_EDIT`, `AR_POSTING`, `AP_POSTING`, `AP_APPROVAL`, `CARRIER_STATUS_EDIT` — are marked enforced on the Users page, and the rest (`AR_CHARGES`, `AP_CHARGES`, `CARRIER_INSURANCE_EDIT`, `NO_AR_INVOICE`) are a record, not a restriction. Two are read by a Lambda as the claim itself: `claim-CREDIT_LIMIT_EDIT` stands in for ADMIN on the customer credit fields in `tmsDirectoryActions`, and `claim-CARRIER_STATUS_EDIT` on a status move in `tmsCarrierActions`. The AR/AP three name gates that `tmsFinanceActions` judges by `arPostingAdminOnly` / `apPostingAdminOnly` / `apApprovalAdminOnly` — the claim records who should post, it does not open that gate.
- `lockoutCheck` refuses the three ways to lock the office out, word for word on the page: the owner (*"The owner's role cannot be changed."* / *"The owner account cannot be disabled."* / *"The owner account cannot be deleted."*), yourself (*"You cannot change your own role."* / *"You cannot disable your own account."*) and the last enabled admin (*"<email> is the last admin — promote somebody else first."*). The admin count is taken from the profiles with Cognito's live enabled flag folded in, so a disabled login does not count. `updateProfile` also refuses a manager who is not another user with a profile: *"A manager must be another user."*
- Other actions: `create` (AdminCreateUser + the `DISPATCHER` default group + a `PENDING` profile with `invitedAt`/`invitedBy`), `reinvite` (RESEND), `resetPassword`, `disable`/`enable` (profile `status` INACTIVE/ACTIVE), `delete` (pool user + profile row; rows they wrote keep their e-mail), `setTeams` (no group change — teams carry no page access), `setDivisions` (no group change either — the OwnershipDivision codes decide which saved Shipment views the person is offered), `setClaims`, `updateProfile` (name, title, phone, DAT e-mail, manager). `list` joins Cognito to the profiles and mints the owner's row if it is missing, so the lock-out check never sees zero admins. Every action writes an `AuditLog` row best-effort, outside the write that matters.
- **Teams** are `TmsSettings.teams` JSON (Settings → Teams), not a table: `{key, name, memberIds[], senderAddresses{shipment, rateCon, quoteReply, customerInvoice, remittance}, showContactOnTracking, active}`, checked by `validateTeams` in the card and again in `tmsDirectoryActions.SAVE_SETTINGS` (unique upper-cased keys ≤ 24 chars, a name, at least one member, no duplicate member, well-formed addresses, ≤ 50 teams). Members are Cognito usernames matched case-insensitively, and the save mirrors membership onto every member's `UserProfile.teamKeys`. The five sender addresses are **stored only** — `senderFor` exists and nothing sends from it until J/L; it looks a team up by key whatever `active` says, so a retired desk keeps its address on the work that named it.
- `limitCustomerRepView` / `limitCarrierRepView` (the two switches on the Roles & pages card) default the boards' "Mine" filter for reps. They are **not** a read restriction: no Lambda refuses a read because of them and every signed-in user can still read every customer, carrier and load.

## Commissions
- `/commissions` (Sales → Commissions, page grant `commissions`) is the ledger and the approval desk; the rows for one invoice also sit on the invoice page (`InvoiceCommissionCard`) with **Preview** and **Recompute**. Every write is a `tmsFinanceActions` action behind its own door — owner / ADMIN / `page-commissions`, decided before the AR/AP page rule, so `page-invoicing` does not fall through — and `SAVE_COMMISSION_SETTINGS` is owner/ADMIN. Nothing is computed, written or shown while `TmsSettings.commissionsEnabled` is false; every action refuses with *"Commissions are turned off. Switch them on in Settings → Commissions first."*
- **The trigger** is `commissionTrigger`: `GENERATE_INVOICE` (default) or `INVOICE_PAID`, which skips an invoice until the order or the invoice carries `paidAt`. Ready-to-invoice is deliberately not offered — nothing is frozen at that rung. The reconcile runs again, best-effort and after the money transaction, from `GENERATE_INVOICE`, `RECORD_PAYMENT`, `WRITE_OFF`, `RECORD_BILL` and `APPROVE_BILL` (the cost side), and `VOID_INVOICE` puts its cancels and reversals inside its own transaction.
- **The number** (`src/lib/commission.ts`, shared by the Lambda and the page): plan resolved user → customer → team → the one unscoped plan, active and inside its effective window, else no rows at all; basis = invoice total **less write-offs** (a credit memo does not reduce it) against the order's `LoadFinancials` cost; a percentage taken once with half-away-from-zero rounding; a role's pot split across its people by largest remainder, so the shares always sum to the pot. A straight tier ladder pays the band the load lands in on the whole basis, a graduated one pays each band its own slice and is refused on margin bands at save time (*"is graduated, which only works on gross-profit bands — a margin ladder has no slice to pay a rate on"*). An own-fleet order under a PERCENT_PROFIT role writes **$0 with `needsReview` and `basisNote: 'OWN_FLEET_NO_COST'`** rather than paying on a 100 % margin; a role naming nobody writes no row.
- **Reconcile rules** (`reconcileCommissions`): a missing row is written, an UN_APPROVED / countered row is rewritten in place under CAS on `version`, a MANAGER_APPROVED-or-later row is never touched and the difference is booked as its own `ADJUSTMENT` (`cma:…`), and a person the records no longer name is cancelled while open and `REVERSAL`ed (`cmr:…`) once approved. Rerunning over unchanged facts writes nothing. `RUN_COMMISSIONS` takes an `invoiceId` or a `month`; `PREVIEW_COMMISSIONS` takes an `orderId` and writes nothing.
- **The ladder** is `commissionState`, read by the page and the Lambda so a visible button is one the server honours: a rep counters their own row, an admin or manager counters anybody's, whoever did not counter last accepts (*"Forbidden: the other side has to answer this counter"*). `APPROVE_COMMISSION` by an admin lands `FULLY_APPROVED`, by a manager `MANAGER_APPROVED`; `ACCEPT_COMMISSION_COUNTER` lands `FULLY_APPROVED` at the countered amount; `OVERRIDE_COMMISSION` needs an amount and a note and keeps `amountCents` beside it; `CANCEL_COMMISSION` needs a reason and a cancelled row counts nowhere. `netCents` is override ?? counter ?? amount. `commissionApprovalAdminOnly` takes managers out of the approval seat.
- **Pay periods**: `OPEN_PAY_PERIOD` (idempotent on `cpp:<periodStart>`) mints the window from `commissionPaySchedule` (`periodWindow`: weeks Monday–Sunday, fortnights from the anchor Monday, semi-monthly 1st–15th / 16th–end, months, then `daysUntilPay` or a monthly `payDay`); `SUBMIT_PAY_PERIOD` claims every `FULLY_APPROVED` row whose `triggerAt` falls in the window, each write conditioned on still being approved and unclaimed, and totals the period by rep; `APPROVE_PAY_PERIOD` then `PAY_PAY_PERIOD`, which requires a reference (*"Paying a period needs the payroll reference it was paid under"*) and stamps the rows `PAID`. **No money leaves this stack** — a paid period records that payroll ran elsewhere. `RENDER_COMMISSION_STATEMENT` writes one rep's PDF to `commissions/<repId>/<periodId>.pdf` and returns a signed download. `commissionPayAdminOnly` (default true) keeps the four period actions with owner/ADMIN.

## TMS Phase 1 — Customers & Locations directory
- `/customers` and `/locations` (page grants `customers` / `locations`) are the reusable directory behind the Load form. Customer carries billing contact/address, MC/DOT, payment terms, credit limit (integer cents — the form parses a decimal string, never a float), credit hold, required invoice documents, default division / sales rep (left blank until the business supplies them), aliases and the appointment workflow (`NONE` | `BATORY`). Location carries the full postal address, Google geocode (lat/lng, timezone, place id, expiry), facility type, hours, appointment rule / lead time, dock / lumper / detention notes, contacts, aliases and any number of linked customers; the legacy `city`/`customerName`/`apptContact*` columns stay as mirrors.
- Every directory write goes through the `tmsDirectoryActions` Lambda (`UPSERT_CUSTOMER`, `UPSERT_LOCATION`, `ARCHIVE_*`, `SAVE_DIVISION`, `SAVE_SETTINGS`, `PREVIEW_MERGE_LOCATIONS`, `MERGE_LOCATIONS`, `RESUME_MERGE`); the Customer/Location/Division/TmsSettings/DirectoryMergeJob models are read-only for signed-in users. Directory writes need owner/ADMIN or a `page-customers` / `page-locations` / `page-loads` grant (load builders can create the customer or facility their load needs); divisions, TMS settings and merges are ADMIN/owner only. Updates send the `updatedAt` the form was opened from; a stale save is refused with "changed by someone else — reload". The server computes `normalizedName` / `normalizedAddress`; a create never silently adopts an existing record — a same-name-and-city or same-address collision is rejected with the existing id so the person picks it or adds an alias. Directory records are archived, never deleted; loads keep their typed customer name and their booked stop address.
- Coordinates are only ever the ones Google returned: the `tmsGeocode` query (Geocoding, Places Autocomplete + Details, Time Zone; server key `GOOGLE_MAPS_API_KEY`) signs each result with `GEOCODE_TOKEN_SECRET`, and `UPSERT_LOCATION` refuses lat/lng without a valid token. A plain postal address without a pin is always allowed. Editing hours/contacts keeps the stored pin; changing the address drops it until the address is searched again. Google results carry a 30-day expiry (`geocodeExpiresAt`); the 150 m duplicate hint and the detail map ignore expired pins, and nothing caches Google content permanently.
- The Location form also has plain street/city/state/zip/country inputs for facilities Google cannot resolve (or while the server key is missing); typing there drops any stored pin, and facility type / appointment rule start as **Not set** rather than a guessed value.
- Load form: the customer picker and each stop's "Directory location" picker suggest matches with a score and reason ("Exact name or alias", "Within 60 m — review facility identity"); nothing is linked until the person picks it, and **+** creates the record inline. Linking a location stamps `stop.locationId` and an immutable `stop.address` snapshot (street/city/state/zip/country, plus lat/lng/timezone/expiry when the pin was fresh) — later directory edits do not rewrite history. Every other stop field (booking proofs, ladder status, Slack thread, arrival/departure) is carried through unchanged. Load writes stay on the generated `createLoad`/`updateLoad` mutations via the store (subscriptions keep every client in sync; last write wins as before). The miles calculator is unchanged (Nominatim + OSRM).
- The Batory ladder is decided by the linked customer's `apptWorkflow` (`requiresApptProofs(load)` in `src/lib/apptQueue.ts`; `Load.customerApptWorkflow` is stamped at read time from the customer list and never stored). A new customer starts with the workflow **Not set** (stored `null`) and the `/batory/i` name match stays in force for its loads until an admin picks `NONE` or `BATORY` on the Customer page; nothing (UI, Lambda, backfill) sets it implicitly. The `appt-report` digest reads the Customer table for the same rule.
- Location detail (chevron on a row): a real Google map pin when `VITE_GOOGLE_MAPS_API_KEY` + `VITE_GOOGLE_MAPS_MAP_ID` are set and the pin is fresh (otherwise it says why), and the load history of every stop linked there. Dwell is shown only from recorded `stop.arrivedAt`/`departedAt`; an appointment time is never presented as a dwell.
- Merging two locations (ADMIN): preview shows how many loads will be repointed; the merge freezes the source (`mergedIntoId`, `mergeJobId`, inactive), then repoints `stop.locationId` load by load through the generated `updateLoad` mutation (IAM) with a CAS condition on each load's `updatedAt`, re-deriving the legacy mirrors, keeping the booked address (plus `mergedFromLocationId`), proofs and ladder state. It runs 25 loads per call and returns `RUNNING` with `remainingCount`; **Resume** continues (re-scanning for anything still pointing at the source) until `COMPLETED`. A load that keeps conflicting fails the job with the load id; resume after the other editor is done. Cycles and merging into an archived/merged target are refused.
- Settings → Divisions / TMS settings (ADMIN) edit `Division` rows and the `TmsSettings` singleton. Nothing is seeded with guessed values: margin floor, default terms, accessorial codes, invoice format and division MC/DOT/remit-to stay empty until entered or seeded from a reviewed file.
- Backfills (`scripts/backfillCustomers.mjs`, `scripts/backfillLocations.mjs`, `scripts/seedDivisions.mjs`): dry-run by default, `--outputs <path>` is required and the repo-root `amplify_outputs.json` (production) is refused; a plan file records the source fingerprint and AppSync endpoint, and `--apply --env test|sandbox|local` re-checks both (`prod`/`production` are blocked). Customers link only on an exact unique normalized match; Batory rows are flagged for reviewer approval rather than auto-tagged. Locations link only on an exact unique facility+city match and never invent coordinates; unresolved rows go to a review report. Load updates use the generated `updateLoad` mutation with `condition: { updatedAt: { eq } }` and rewrite only `customerId` / stop links, re-deriving mirrors. `--help` runs offline.
